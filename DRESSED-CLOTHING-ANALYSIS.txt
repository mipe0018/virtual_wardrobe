1. PURPOSE, SCOPE AND READ-ONLY GUARANTEE
================================================================================
Goal: diagnose why AI-generated clothing does not consistently fit the
canonical DRESSED body when rendered in the fitting room (wardrobe page),
the profile outfit preview, and the closet flow.

In scope: the full clothing path — upload of a source garment photo,
AI "AI-ready" generation of a transparent clothing layer, storage/versioning,
closet selection, outfit saving, and rendering/transform in the fitting room
and profile preview.

Out of scope (present but not part of the fit question): quota/usage logic,
RLS, auth, moderation, background-function plumbing — except where they gate
or shape the geometry path.

Explicitly NOT done: no fixes, no prompt edits, no CSS edits, no anchor edits,
no DB/migration edits, no master-form edits. This report only observes.

2. METHOD AND EVIDENCE TIERS
================================================================================
Every claim is tagged with one of five tiers:

  [C-CODE]  CONFIRMED BY CODE — read directly in the current working tree,
            quoted with file:line.
  [C-MEAS]  CONFIRMED BY MEASUREMENT — produced by pixel measurement scripts
            (pngjs) this session, or quoted from analysis/ documents with the
            method stated.
  [D-INT]   DOCUMENTED INTENT — stated in a code comment, prompt string or
            analysis/ markdown; proves intent, not behaviour.
  [L-HYP]   LIKELY HYPOTHESIS — consistent with evidence but not yet isolated
            by a discriminating test.
  [U]       UNKNOWN — cannot be decided from the repository alone.

Measurement method (this session): Node + pngjs scripts in %TEMP%
(dressed-figure.js, dressed-clothes.js, dressed-measure.js, dressed-sample.js):
  * Base forms are RGB line drawings on white; figure = pixel differing from
    the row's estimated background (max channel delta > 22).
  * Clothing assets are RGBA; extent = alpha > 8 (permissive).
    analysis/Phase2-Woman-Tshirt-Test.md shows alpha >= 128 is the correct
    "solid garment" threshold and alpha > 1 overestimates by ~+9.8% width /
    +33% height due to alpha haze. Differences are noted explicitly.

Limitations: no browser run (no visual overlay observed this session), no
live database queried, no new AI generation performed, and no male clothing
assets exist in the repository (section 15).

6. THE RENDERING / COMPOSITING MODEL
================================================================================
Fitting room container (wardrobe.css:608-626):
  .dressed-canvas { aspect-ratio: 2/3; width: min(100%, 493.333px) }
  .dressed-canvas img { position:absolute; inset:0; object-fit:contain }
  => a 1024x1536 image fills the box exactly 1:1 (both are 2:3). [C-CODE]

Layer transform (wardrobe.css:640-653):
  --clothing-base-scale: var(--dressed-clothing-scale, 1);          // :648
  transform-origin: calc(var(--anchor-x,0.5)*100%) calc(var(--anchor-y,0.2)*100%);
  transform:
    translate(var(--clothing-x,0%), var(--clothing-y,0%))
    scale(calc(var(--clothing-base-scale) * var(--clothing-scale,1)));

Variable resolution today [C-CODE]:
  --dressed-clothing-scale : never set anywhere in src/ -> fallback 1
  --clothing-scale         : placement.scale = NEUTRAL 1 (all 23 categories)
  --clothing-x / -y        : placement.x/y = NEUTRAL 0 -> translate(0,0)
  profile.css:616          : base scale hard-coded 1 (profile preview)
  => effective transform = identity for every layer in every category.

Math (also proven in analysis/ClothingPlacement-Implementation-Analysis.md §3):
  scale(1) about origin A maps L -> A + 1*(L-A) = L for every A and L.
  => transform-origin (the anchor), translate, and scale are ALL no-ops.
  The browser shows the asset's raw canvas rectangle. [C-MEAS / proof]

Historical context: HEAD~ (commit d973d1b "working solution with size") used
base scale 0.56, which compressed every garment to 56% of its extent around
the anchor; analysis/ proves joggers were mathematically impossible under
0.56 (bottom would need to be at 1990px on a 1536px canvas). The working tree
changes both CSS files to 1 (uncommitted, see Repository State). [C-MEAS]

Also present but inert: a 7px horizontal offset — body centre of both masters
is x≈504-505 px vs canvas centre 512 px, so every overlay sits ~0.6% right of
the drawn body (documented as Problem C in analysis/BestFitAnalyse-Woman.md).
[C-MEAS]

7. ANCHOR SYSTEM AND GENDER-SPECIFIC ANCHOR COMPARISON
================================================================================
Anchors are body points expressed as canvas fractions (0-1), defined once in
clothing-categories.ts:86-104 (DRESSED_ANCHORS). Each category maps to one
anchor via CLOTHING_PLACEMENT (lines 154-177); all categories use
NEUTRAL = {scale:1, x:0, y:0} (line 152). [C-CODE]

  head 0.10 | face 0.14 | ears 0.14 | neck 0.185 | shoulders 0.22
  torso 0.27 | waist 0.42 | hips 0.46 | dress 0.20 | knees 0.72
  ankles 0.91 | feet 0.95 | left-hand (0.33,0.5) | right-hand (0.67,0.5)
  full-body 0.5

Gender handling [C-CODE]: dressedAnchor(anchor, baseType) (lines 135-143)
returns the shared value for "woman" or unknown, and for "man" substitutes
MAN_ANCHOR_Y (lines 122-129): neck 0.17, dress 0.175, shoulders 0.20,
torso 0.25, waist 0.40, hips 0.44. Knees/ankles/feet/head/face/ears/hands are
deliberately shared — the code comment (lines 108-121) states both figures
have the same head top (y≈0.021), the same centre (x≈0.5), and that the man's
shoulder line sits higher (y≈0.176). [D-INT]

Category -> anchor map: tops/shirts/sweaters -> torso; jackets -> shoulders;
dresses -> dress; skirts/shorts -> hips; pants -> waist; socks -> ankles;
shoes -> feet; bags -> right-hand; jewelry/necklaces -> neck; earrings -> ears;
bracelets/watches -> left-hand; glasses/sunglasses -> face; hats/hair ->
head; accessories/other -> full-body. [C-CODE]

11. WHAT WORKS AND WHAT DOES NOT

WORKS (evidence-backed) [C-CODE unless noted]:
 W1 Canvas discipline of generated layers: always 1024x1536, transparent
    corners, horizontally centred (C-MEAS 9.1).
 W2 Master selection: clothing layers and characters are generated against the
    correct per-gender master, loaded from storage with a hard 1024x1536 check
    (base-forms.ts:53-55, clothing-job.ts:68, character-job.ts:94).
 W3 Gender gating end-to-end: baseType must equal the primary character's
    gender (process-clothing.ts:281-291); assets are keyed by base_type and the
    UI only shows aiReadyAssets[baseType] (wardrobe.astro:209,
    profile-outfits.ts:27, items/index.ts:264-267).
 W4 Legacy geometry is blocked: contract version enforced at generation, outfit
    save, item listing, character reuse and in the UI (section 5).
 W5 Anchors match the masters: shared table derived from woman.png matches to
    <0.001 for torso/waist/hips; MAN_ANCHOR_Y compensates man differences
    (section 7, C-MEAS).
 W6 Wardrobe and profile render identically (same anchor source, same math,
    same identity transform).
 W7 Layer ordering is deterministic and category-based (z-index/insertion).
 W8 Compositing transform is now the identity (scale 1) — no more 0.56
    compression distortion of correct assets (working-tree change, section 6).

DOES NOT WORK (the observed symptom, decomposed):
 F1 Garment layers are systematically TOO LARGE vertically for the master's
    body region: tops measured ~2x the correct height in two independent
    tests (9.2, 9.3) [C-MEAS] — a shirt's hem lands near the knees/thighs.
 F2 Garment bboxes are inconsistent between assets (9.1): even same-category
    items span 0.174-0.212 top and 0.656-0.787 bottom, so nothing can be tuned
    per category [C-MEAS].
 F3 NOTHING in the pipeline can correct F1/F2 at render time: the transform is
    the identity, so errors pass through 1:1 (section 6) [C-CODE].
 F4 NOTHING rejects a bad asset at generation time: validation is format-only
    (section 10.2) [C-CODE].
 F5 The character rendered underneath is itself an unvalidated AI product;
    if it drifts from the master, correctly generated garments would still
    misfit [C-CODE gap; magnitude UNMEASURED — L-HYP].
 F6 Small but constant ~7 px horizontal offset (body centre vs canvas centre)
    [C-MEAS].
 F7 Alpha haze around garments (faint ghost pixels) [C-MEAS].
 F8 Male pipeline has zero empirical coverage: no male assets exist to verify
    man.png + MAN_ANCHOR_Y end-to-end [U].

Mapping symptom -> step: F1/F2/F4 -> step 11/12; F3 -> step 20; F5 -> step 2;
F6 -> steps 8.5/9.3; F7 -> step 12 gate (haze pixels alpha>0 pass);
F8 -> data gap.

12. ROOT CAUSE (STRUCTURED, EVIDENCE-TIERED)
================================================================================
12.1 WHAT WORKS (so it can be excluded as the cause)
  * Canvas size, transparency gates, master loading and per-gender master
    selection (W1-W2) [C-CODE]
  * Gender/baseType gating and asset versioning (W3-W4) [C-CODE]
  * Anchor tables match their masters (W5) [C-MEAS]
  * Renderers agree with each other (W6) [C-CODE]
  * The compositing transform no longer distorts (identity, W8) [C-CODE]
  => The container, the plumbing, the gating and the anchors are NOT the
     problem. Compositing contributes exactly 0 px of error today.

12.2 WHAT DOES NOT WORK
  F1-F4 (sections 9, 10, 11): generated garment geometry deviates from the
  master's body region — systematically too tall (~2x), inconsistently bboxed
  across assets — and no step in the pipeline either rejects, normalizes, or
  corrects it. Plus F5 (unvalidated character geometry), F6 (7px), F7 (haze),
  F8 (no male data).

12.3 STRONGEST EVIDENCE
  E1 [C-MEAS] tshirtwoman.png regenerated through the UNCHANGED pipeline:
      solid height 796 px vs the master's correct top region 396 px (2.01x),
      bottom +358 px below the hip line, top 42 px above the shoulder line
      (analysis/Phase2-Woman-Tshirt-Test.md §4, §8 P6-P8).
  E2 [C-MEAS] Repetition: tshirt.png (older) shows the SAME error region
      (0.1816-0.6549 vs 0.1751-0.6934) — this is a stable model behaviour,
      not a sample fluke (Phase2 §4.3, §8 P12, §9 O2-O5).
  E3 [C-MEAS] Variability across the 8 repo assets: top 0.107-0.316,
      bottom 0.656-0.949, width 447-937 px (section 9.1) — there is no common
      asset frame to calibrate a constant against.
  E4 [C-CODE] clothing-job.ts:118-153 validates format and alpha only —
      nothing geometric — while the prompt (lines 79-81, 112) demands
      pixel-for-pixel alignment. Intent and enforcement do not meet.
  E5 [C-CODE] wardrobe.css:640-653 resolves to scale(1)/translate(0,0)
      (--dressed-clothing-scale never set; NEUTRAL scale 1), so rendering
      cannot compensate for E1-E3 (section 6; proof in
      analysis/ClothingPlacement-Implementation-Analysis.md §3).
  E6 [C-CODE] character-job.ts:105-117: the character — the body actually
      rendered — is validated for format only.

12.4 MOST LIKELY ROOT CAUSE (primary)
  [L-HYP, built on C-CODE + C-MEAS]
  The pipeline delegates ALL geometric correctness of the overlay to
  natural-language prompting of a diffusion model at BOTH generation sites
  (garment layer and character), then enforces only file-format invariants
  and renders with an identity transform. The model reliably honours canvas
  size and centring but NOT the pixel-for-pixel body registration the prompt
  demands: garments come out roughly 2x too tall and with an unpredictable
  bounding box (E1-E3). Because there is no deterministic gate (E4), no
  normalisation step, and no compensating renderer (E5), every generation
  error reaches the screen 1:1 — so fit is inconsistent by construction:
  each regeneration can land differently (F2), and one category that is
  correct by luck stays correct only by luck.
  In one sentence: FIT IS NEVER ENFORCED ANYWHERE — it is only requested.

12.5 ALTERNATIVE / CONTRIBUTING HYPOTHESES (ranked)
  A1 [L-HYP] Character drift: the personal character (rendered body) deviates
      from the master that the garment was fitted against. Plausible —
      format-only validation (E6) and a heavily rewritten prompt in the
      working tree suggest prior attempts to fight exactly this. Magnitude
      UNMEASURED (no character PNGs in repo). Could alone explain "sometimes
      fits, sometimes doesn't" across users/characters.
  A2 [C-MEAS, minor] ~7 px horizontal offset from body centre vs canvas centre.
  A3 [C-MEAS, minor] Alpha haze creating apparent over-size / ghosting when
      measurements or eyeballing include faint pixels.
  A4 [C-CODE, historical] The 0.56 base scale in committed HEAD (d973d1b)
      compressed garments to 56%; already fixed to 1 in the working tree but
      NOT committed — deployed builds from HEAD still compress. Verify which
      build the user observed before accepting this as current.
  A5 [L-HYP] Category anchors (shoulders 0.22 vs measured 0.2025 for woman)
      would misplace layers IF any non-1 scale were re-enabled; inert today.
  A6 [U] Model-side variance per source photo (flat-lay vs worn garment) as an
      additional driver of F2; only one source per test was available.

12.6 DISCRIMINATING EVIDENCE (what would prove or disprove each candidate)
  D1 (separates primary cause from A1): download one stored character PNG
      (dressed_characters.model_path) and measure its shoulder/waist/hip rows
      against the master (method of section 8).
      -> if within ~±0.01: character is fine, garment geometry is the sole
         driver (primary cause confirmed).
      -> if drifted: both ends are broken; A1 becomes co-primary.
  D2 (confirms the "no enforcement" mechanism): generate the same garment
      twice and measure both assets. Primary cause predicts large inter-run
      variance (E3); if both runs are nearly identical AND correct, the
      problem lies elsewhere (e.g. rendering, A4 build state).
  D3 (isolates A4): confirm which build is observed — does the served CSS
      contain 0.56 or 1? (search built assets for "clothing-base-scale").
  D4 (isolates A2/A3): overlay one asset on the master in an image editor at
      1:1 and measure horizontal shift with alpha>=128 bounds only.
  D5 (male path): generate one male asset through the unchanged pipeline and
      measure against man.png (currently fully UNKNOWN, F8).

12.7 SMALLEST SAFE CHANGE (recommendation only — NOT implemented)
  Ranked by (expected fit gain) / (risk):
  R1 Add a deterministic post-generation geometry gate + normalisation inside
     clothing-job.ts right after the existing validation (clothing-job.ts:118):
     compute the solid (alpha >= 128) bbox of the returned layer, compare it
     with a per-category reference region derived from the master (values in
     sections 8.4 and analysis/), and either (a) reject and retry, or
     (b) scale/translate the layer so its shoulder line lands on the master's.
     This converts "fit requested" into "fit enforced" at the exact point
     where the error is already measured (E1-E4), touches one file, and does
     not alter prompts, masters, anchors, CSS or the DB.
  R2 (smaller still, informational) log/record the measured bbox alongside
     wardrobe_item_ai_assets so drift is observable per asset.
  R3 (complementary) apply the same geometric check to characters in
     character-job.ts (D1) before publish_dressed_character.
  R4 Commit-or-revert decision for the already-made working-tree changes
     (scale 0.56 -> 1, dressedAnchor/MAN_ANCHOR_Y) so every environment
     runs one coherent compositing model (A4).
  None of these were made in this session.

12.8 DO NOT CHANGE (until the discriminating evidence above exists)
  * The master PNGs woman.png / man.png — they are the geometry authority and
    every measured anchor/region derives from them [C-MEAS].
  * DRESSED_GEOMETRY_CONTRACT_VERSION and the gating in section 5 — they
    correctly keep legacy bodies out [C-CODE].
  * The 39-string clothing prompt — it is byte-identical since 3193b8a and is
    the control variable of every measurement so far; changing it would
    invalidate the analysis baseline [C-MEAS].
  * Anchor tables / MAN_ANCHOR_Y / NEUTRAL placement — currently inert (E5);
    "fixing" them cannot change what is on screen and risks breaking the
    correct-by-measurement woman anchors [C-MEAS].
  * Layer order, asset versioning, storage layout — orthogonal to fit.
  * The current identity transform (scale 1): reintroducing a global scale
    would recreate the mathematically impossible case proven for joggers in
    analysis/BestFitAnalyse.md §10.5.
