3. TARGET ARCHITECTURE
================================================================================
Two clearly separated zones, connected only by an opaque deletion id:

  ZONE A — ACTIVE (belongs to a live auth user)
  auth.users (identity: email + password, Supabase-managed)
    └── profiles 1:1 (FK -> auth.users ON DELETE CASCADE, verified in M0/M1)
          └── dressed_characters ── model_path ──> {uid}/personal-model-*.png
          └── wardrobe_items ── original/preview paths (ACTIVE files)
                └── wardrobe_item_ai_assets (reusable, base_type keyed)
          └── saved_dressed_outfits, wardrobe_results, ai_generation_usage
          RLS: auth.uid() = user_id everywhere; storage under `{uid}/` only.

  ZONE B — RETAINED (exists only after account deletion; NO identity)
  account_deletions (deletion_id, source uid, phase, timestamps)
    ├── retained_wardrobe_items (deletion_id, item_id, category)
    └── retained_assets (deletion_id, kind, base_type, generation_version,
                         source_path, retained_path, retained_at)
          └── storage: model-images/retained/{deletion_id}/...
  RLS: enabled with ZERO policies (deny-all) for anon+authenticated;
  service_role only. No user_id, no email, no name in Zone B.

  ZONE C — COOLDOWN (enforcement only)
  deleted_emails (email_digest PK, deleted_at, available_at, deletion_id)
  + a SECURITY DEFINER BEFORE INSERT/UPDATE trigger on auth.users.
  Deny-all RLS; readable only inside the trigger function.

Flow:  account deletion = copy what must be preserved (A -> B), record the
       cooldown (C), delete the auth user (cascades A), sweep `{uid}/`
       storage. The email returns to service after available_at, creating a
       FRESH Zone A under a brand-new uid — never re-linked to Zone B.

Design choice (options compared in sections 6 and 8):
  RECOMMENDED = hard-delete auth.users at deletion time + DB-side cooldown
  table/trigger for the 7-day block + detached retention snapshot.
  Rejected alternatives: (i) soft-delete shell user kept forever, (ii)
  cron-based delayed auth delete, (iii) in-place nullable-owner retention
  columns, (iv) frontend-only email blocking. Reasons in sections 6/8.

4. AUTH AND LOGIN
================================================================================
 - Supabase Auth remains the ONLY authentication system. Email is the login
   identity; passwords remain exclusively in auth.users — never copied to
   profiles or any DRESSED table. [unchanged — CONFIRMED BY CODE]
 - Existing signup/login/logout flows (signup.astro, login.astro,
   session handling, authenticateSupabaseRequest Bearer validation) are
   NOT modified. No new identity table, no second login path, no
   parallel user id. [requirement: existing login/signup preserved]
 - auth.uid() stays the single foreign key used by every DRESSED table.
 - profiles stays the 1:1 application profile. Target change (M1): ensure
   profiles.user_id has a verified FK -> auth.users(id) ON DELETE CASCADE
   and a uniqueness guarantee on user_id, with the definition captured in
   version control. M0 first verifies what the live schema actually has
   [UNKNOWN — audit F37]; if the FK already exists, M1 becomes a no-op
   guard migration. Profile CREATION stays client-side insert-if-missing
   (profile.astro:633-646) — it works today and changing it is not
   required by any requirement; an optional AFTER INSERT trigger on
   auth.users (idempotent, ON CONFLICT DO NOTHING) is listed in section 16
   as OPTIONAL hardening only.
 - New users: signUp(email, password, metadata) -> auth row -> cooldown
   trigger check (section 8, passes for everyone except recent deletions)
   -> profile created on first /profile visit. Nothing else changes.
 - Existing users: zero change — same uid, same profile, same sessions,
   same login. No migration touches auth.users rows.
 - Account deletion (new) runs server-side with the service role and ends
   with auth.admin.deleteUser(uid): the user can no longer log in, refresh
   tokens die with the user row, and any still-live access token expires
   within Supabase's short JWT lifetime (see risk R6).

5. USER DATA
================================================================================
Layout principle (unchanged, just made explicit):
  - Identity data  : auth.users only (email, password hash, metadata).
  - Active data    : every DRESSED row keyed user_id -> auth.uid();
    every storage file under `{uid}/`. RLS `auth.uid() = user_id`.
  - Retained data  : detached rows keyed deletion_id (section 7); files
    under `retained/{deletion_id}/`. No identity fields at all.
  - Cooldown data  : hashed email + timestamps (section 8).

Ownership rules that stay exactly as today:
  - wardrobe_items / assets / characters / outfits / results / usage:
    owned directly by the user, cascade on auth delete (audit 4.1).
  - saved outfits and legacy assets: owned transitively via character/item.
  - system-reference base forms and ai_generation_limits: platform-global.

No parallel or competing identities are created:
  - Zone B rows have NO user_id and NO email — they cannot be read by, or
    attributed to, any account, including a future account that reuses the
    same email. After 7 days the email produces a NEW uid with an EMPTY
    Zone A; the old generated assets stay invisible in Zone B.
  - account_deletions keeps the old source uid ONLY as an opaque retry
    handle for the storage sweep (uuid without email/name); it is
    deny-all to clients (section 10).

6. ACCOUNT DELETION
================================================================================
Requirement: active profile removed/deactivated, user loses access to the
old private account, AI-generated images preserved, no cascade-destroy of
generated assets, no orphaned storage.

6.1 OPTIONS COMPARED (decision record)

 OPTION A — Hard delete + detached retention (RECOMMENDED)
   Delete auth.users via admin API AFTER snapshotting generated assets
   into Zone B; sweep `{uid}/` storage; block the email 7 days with a DB
   trigger (section 8).
   + No shell auth rows; no cron; email lifecycle controlled by our own
     DB; PII removed (profile, source photo, name, metadata die with the
     auth row); retained assets provably unreachable by anyone.
   - Requires explicit copy steps (rows + files) before deletion.
   - Supabase's native email uniqueness disappears with the row, so the
     7-day rule MUST be enforced by us — it is, inside the database.

 OPTION B — Soft-delete shell user (disabled, email anonymised, kept)
   + Retention free (FKs intact; no copying).
   - Leaves disabled auth rows forever (explicitly undesirable); needs
     manual PII scrubbing; still needs OUR cooldown table because the
     anonymised email frees the original immediately (native uniqueness
     does NOT span the 7-day window); active session revocation required.

 OPTION C — Delayed delete (keep auth row 7 days; cron deletes at D+7)
   + Native uniqueness blocks signup during the window.
   - Cron dependency: a missed run recreates the permanent "user already
     exists" bug (audit F27); account stays alive for 7 days unless
     separately disabled (extra moving parts); no standalone source of
     truth for the cooldown.

 OPTION D — In-place retention (nullable user_id / SET NULL FKs)
   - Breaks NOT NULL columns and composite PKs
     (user_id,item_id,base_type); forces RLS + query rewrites app-wide;
     mixes active and retained rows in one table. Rejected as least-safe.

 => RECOMMENDATION: OPTION A — the only option satisfying ALL
    requirements at once (immediate access loss, no lingering auth users,
    guaranteed non-cron 7-day blocking, PII minimisation, explicit
    retention) with purely ADDITIVE schema changes (trivial rollback).

6.2 THE DELETION FLOW (server-side, service role; phased & idempotent)
 New endpoint: POST /api/account/delete (authenticated user).
 New orchestrator: src/lib/server/account-deletion.ts.
 Every phase is recorded in account_deletions.phase so a crash can be
 retried safely (re-running a done phase is a no-op).

 P0 VERIFY  - valid Bearer session + password re-entry confirmed with
              signInWithPassword server-side; otherwise reject.
 P1 LEDGER  - INSERT account_deletions(source_user_id=uid,
              phase='initiated') [reuses an earlier failed attempt].
 P2 RETAIN  - COPY (never move): rows -> Zone B (matrix, section 7);
              files -> model-images/retained/{deletion_id}/...;
              verify every retained file exists + row counts match.
            -> phase='retained'. ANY mismatch aborts: nothing deleted.
 P3 COOLDOWN - INSERT deleted_emails(digest(lower(email)),
              available_at = now() + 7 days, deletion_id)
            -> phase='cooldown_set'. Deliberately BEFORE the auth delete:
              a crash here leaves a live user whose email is additionally
              cooldown-blocked — safe and retryable (Supabase already
              blocks signups while the auth row exists).
 P4 DELETE  - service client auth.admin.deleteUser(uid) -> cascades every
              application row (audit 4.1); profiles deleted explicitly
              first IF M0/M1 shows no FK.
            -> phase='auth_deleted'. Login impossible from here; refresh
              tokens die with the user row.
 P5 SWEEP   - list + remove ALL objects under `{uid}/` in BOTH buckets
              (paginated, idempotent): source photo, originals, previews,
              models, assets, results — Zone B holds copies. Defensive
              reverse-lookup first (audit 18 hard rule): if any remaining
              DB row still references a path, skip it and phase='failed'.
            -> phase='storage_swept'.
 P6 VERIFY  - storage objects under `{uid}/` == 0 in both buckets;
              retained file count == expected; cooldown row present.
            -> phase='verified', completed_at=now().

 ROLLBACK BOUNDARY: before P4 the deletion can be cancelled (delete the
 cooldown row, mark account_deletions 'cancelled'; user still logged in).
 After P4 the ACCOUNT is irreversibly gone (by design); only Zone B can be
 purged later via the admin path (risk R8).

6.3 WHAT HAPPENS TO EACH ENTITY ON DELETION
  profiles row                    -> deleted (cascade or explicit) [active]
  dressed_characters rows         -> cascade; model FILES copied to Zone B
  wardrobe_items rows             -> cascade; original+preview files swept;
                                     preview FILE copied to Zone B
  wardrobe_item_ai_assets rows    -> cascade; asset FILES copied to Zone B
  wardrobe_item_ai_assets_legacy  -> cascade; FILES copied
  saved_dressed_outfits rows      -> cascade (no files)
  wardrobe_results rows           -> cascade; FILES copied
  FASHN try-on files (no row)     -> copied via storage listing, then swept
  ai_generation_usage / overrides -> cascade (counters meaningless without
                                     the account — deliberately NOT retained)
  source photo / clothing originals -> deleted, never retained (user uploads)

  generated character/model image     | dressed_characters.model_path | YES

7.2 ZONE B TABLES (exact design; account_deletions created by migration M2,
    the retained_* tables created EMPTY by migration M3)

  public.account_deletions
    deletion_id     uuid PK default gen_random_uuid()
    source_user_id  uuid NOT NULL   -- opaque retry handle; NO FK (must
                                    -- survive the auth.users delete)
    phase           text NOT NULL default 'initiated'
                    CHECK IN ('initiated','retained','cooldown_set',
                              'auth_deleted','storage_swept','verified',
                              'failed','cancelled')
    error           text NULL
    started_at      timestamptz NOT NULL default now()
    completed_at    timestamptz NULL
    retained_count  integer NULL

  public.retained_wardrobe_items
    deletion_id  uuid NOT NULL REFERENCES account_deletions
                 ON DELETE CASCADE
    item_id      text NOT NULL      -- original wardrobe_items.id value
    category     text NULL          -- category kept; item NAME dropped
    created_at   timestamptz NULL
    PRIMARY KEY (deletion_id, item_id)

  public.retained_assets
    id                 uuid PK default gen_random_uuid()
    deletion_id        uuid NOT NULL REFERENCES account_deletions
                       ON DELETE CASCADE
    item_id            text NULL    -- soft link to retained item
    kind               text NOT NULL CHECK IN ('character_model',
                       'clothing_asset','legacy_clothing_asset',
                       'clothing_preview','dress_result','tryon_result')
    base_type          text NULL CHECK IN ('woman','man')
    category           text NULL
    generation_version integer NULL
    source_path        text NOT NULL  -- original path (audit trail)
    retained_path      text NOT NULL UNIQUE
                       -- always under retained/{deletion_id}/
    source_created_at  timestamptz NULL
    retained_at        timestamptz NOT NULL default now()
    UNIQUE (deletion_id, source_path)
  [composite FK (deletion_id,item_id) -> retained_wardrobe_items optional;
   added only where item_id is set — keeps Zone B self-consistent]

  FIELDS DELIBERATELY ABSENT: user_id, email, name, photo metadata,
  character names. Zone B holds only the technical metadata needed to
  interpret a retained image. [PII minimisation + clear separation]

7.3 OWNERSHIP AFTER ACCOUNT DELETION (explicit answer)
  - Retained assets are owned by THE PLATFORM under a product/legal
    retention decision, referenced ONLY by deletion_id. No user — living
    or future — owns, reads or links them: RLS deny-all, service-role
    access only (section 10), and application code NEVER mints a signed
    URL for any retained_path.
  - The old uid keeps NO reference: source_user_id exists only inside
    account_deletions as an opaque retry/audit handle; it is invisible to
    all clients and carries no email/name.
  - A future account re-using the email receives a NEW uid and an EMPTY
    Zone A. There is deliberately no join from any identity to Zone B —
    retention and identity are permanently decoupled.
  - Erasure path: service role may delete account_deletions (cascades all
    retained rows) + the retained files — documented as the admin/legal
    purge mechanism (risk R8).

8. 7-DAY EMAIL RESTRICTION
================================================================================
Requirement: after account deletion the same email cannot sign up for 7
days; afterwards it can; enforcement server/database-side, not frontend;
no lingering active auth users; no bypass path.

8.1 WHY SUPABASE'S NATIVE UNIQUENESS IS NOT ENOUGH
  Supabase/GoTrue enforces email uniqueness only WHILE a row exists in
  auth.users. Our deletion removes that row (requirement: no lingering
  auth users), so from T+0 the email is natively free — the 7-day window
  must be enforced by an additional bypass-proof database mechanism.
  [CONFIRMED BY CODE: signup uniqueness today comes solely from
  auth.users — audit 1.7]

8.2 OPTIONS COMPARED
  (a) BEFORE INSERT trigger on auth.users (RECOMMENDED)
      A SECURITY DEFINER function raises an exception when the new email's
      digest is found in deleted_emails with available_at > now().
      + Lives in the same database that receives EVERY signup path
        (password, OAuth, admin createUser all INSERT into auth.users) —
        no client can bypass it; no cron; no plan/infra dependency.
        Triggers on auth.users are the standard Supabase pattern (e.g.
        handle_new_user); privileges must be validated on staging (M0,
        audit F37).
      - The exception surfaces to the client as a generic GoTrue error;
        a UX pre-check provides friendly copy (8.4).
  (b) Supabase Auth Hook "Before User Created" (HTTP hook)
      + First-class feature; friendly rejection payloads.
      - Needs plan availability + an extra endpoint + fail-open/closed
        decisions — more moving parts. FALLBACK if (a) is impossible.
  (c) App-level signup endpoint checking the table then calling
      admin.createUser
      - The public GoTrue password-signup endpoint stays open, so direct
        API calls bypass it. REJECTED as sole enforcement; OK only as UX
        pre-check layer.
  (d) Frontend-only check — forbidden by requirement, trivially
      bypassable. REJECTED.

  => RECOMMENDATION: (a) authoritative; (c) optional UX pre-check;
     (b) documented fallback.

8.3 THE MECHANISM (exact objects; created by migration M2, which also
  creates account_deletions because deleted_emails references it)

  public.deleted_emails
    email_digest   text PK            -- hex sha256 of lower(btrim(email))
    deleted_at     timestamptz NOT NULL default now()
    available_at   timestamptz NOT NULL   -- deleted_at + interval '7 days'
    deletion_id    uuid NULL REFERENCES account_deletions(deletion_id)
    -- RLS enabled, ZERO policies; revoke all from anon+authenticated;
    -- service_role SELECT only (audit 12.9 deny-all pattern)

  public.dressed_email_digest(p_email text) returns text
    -- IMMUTABLE: encode(sha256(lower(btrim(p_email))), 'hex')
    -- digest (not raw email) keeps the cooldown table free of readable
    -- PII; the table is deny-all to clients anyway (decision 15.R5).

  public.enforce_email_cooldown() returns trigger
    -- SECURITY DEFINER, set search_path = ''
    -- IF EXISTS (SELECT 1 FROM public.deleted_emails
    --            WHERE email_digest = dressed_email_digest(NEW.email)
    --              AND available_at > now())
    -- THEN RAISE EXCEPTION
    --   'This email was used to delete a DRESSED account and is
    --    temporarily unavailable for new signups.'
    -- EXECUTE revoked from public/anon/authenticated.

  Triggers (BOTH required — signup AND later email change):
    trg_email_cooldown_insert  BEFORE INSERT ON auth.users
      FOR EACH ROW EXECUTE FUNCTION enforce_email_cooldown();
    trg_email_cooldown_update  BEFORE UPDATE OF email ON auth.users
      FOR EACH ROW EXECUTE FUNCTION enforce_email_cooldown();

  Row lifecycle: NO cron. The check compares now() against available_at;
  after 7 days the trigger simply allows the insert. Stale rows with
  available_at in the past are inert (optional later purge job).

8.4 END-TO-END TIMELINE
  T+0      deletion P3 inserts the cooldown row (available_at = T+7d),
           P4 deletes the auth user, P5 sweeps storage.
           Signup with same email -> GoTrue INSERTs -> trigger raises ->
           BLOCKED server-side. Old login -> user not found -> BLOCKED.
  T+6d23h  signup -> still blocked (available_at not passed).
  T+7d+    signup -> trigger passes -> NEW auth user (brand-new uid) ->
           normal profile flow; Zone A empty; Zone B unreachable. Email
           fully usable again.
  UX copy: optional GET /api/account/signup-status?email=... calling
           SECURITY DEFINER signup_email_status(email) returning
           {blocked, available_at} ONLY for cooldown hits (never reveals
           whether a live account exists) so signup.astro can show
           "This email is locked until <date>". Presentation only —
           enforcement stays in the trigger.

8.5 EDGE CASES HANDLED
  - Case/whitespace: digest normalises lower+trim; GoTrue normalises too.
  - Crash after P3 before P4: user still active; retry resumes (P3
    idempotent). The extra cooldown is harmless (Supabase already blocks
    signups while the auth row exists).
  - Crash after P4 before P5: account gone, cooldown set; storage swept on
    retry via account_deletions.phase.
  - Concurrent double deletion: ledger upsert; run is idempotent.
  - OAuth signup with the same email during the window also INSERTs into
    auth.users -> same trigger -> blocked (consistent with "same email").
  - Internal/admin creation with a cooled-down email: explicitly run
    `UPDATE deleted_emails SET available_at = now()` first (service-role
    escape hatch; documented, never automatic).

9.2 OWNERSHIP RULES
  - `{uid}/` prefix <=> user_id column (audit 19, rule 6): only that
    user's policies can reach those objects.
  - `retained/{deletion_id}/` has NO uid and NO active table pointing at
    it -> by the same rule it must carry NO authenticated policy; access
    = service role only; application code never signs such paths.
  - system-reference: read-only for authenticated (existing 0010 policy).

9.3 ACCOUNT DELETION AND STORAGE
  Order: COPY (P2) -> rows die (P4) -> DELETE originals (P5) -> VERIFY
  (P6). A file is never deleted before its retained copy is verified and
  never while a surviving DB row still references it (reverse-lookup
  guard, audit section 18). All deletes are idempotent, so P5/P6 retry
  safely after a crash. This closes the account-deletion members of the
  audit's orphan classes (auth-delete orphans, crash windows,
  failed-remove-after-row-delete) — problem P3 of section 2.

10. RLS AND SECURITY
================================================================================
10.1 ZONE B + C TABLES (new) — deny-all pattern (audit 12.9 exemplary)
  account_deletions, retained_wardrobe_items, retained_assets,
  deleted_emails:
    ALTER ... ENABLE ROW LEVEL SECURITY;
    NO policies created ("RLS with zero policies denies everything").
    REVOKE ALL ... FROM anon, authenticated;
    GRANT SELECT, INSERT, UPDATE, DELETE ... TO service_role;
  enforce_email_cooldown() + dressed_email_digest(): SECURITY DEFINER with
  `set search_path = ''`; EXECUTE revoked from public/anon/authenticated
  (trigger functions fire automatically; nobody can call them directly).
  signup_email_status() (optional UX): SECURITY DEFINER, EXECUTE granted
  to anon+authenticated; returns cooldown info only — never reveals
  whether a live account exists.

10.2 ACTIVE ZONE TABLES — NO CHANGE (hard requirement: no weakening)
  dressed_characters, wardrobe_items, wardrobe_results,
  saved_dressed_outfits, ai_generation_limits/usage, profiles: audit
  12.1-12.10 policies stay exactly as they are (own-row
  `auth.uid() = user_id`; privileged writes only via SECURITY DEFINER
  RPCs).
  ONE tightening (M4): drop "Users can delete their own base-type
  clothing assets" from wardrobe_item_ai_assets so a client can never
  delete a row without its file (audit 12.4/F08). The app never calls
  that path [CONFIRMED BY CODE] — no functionality regresses.

10.3 GUARANTEES MAPPED TO REQUIREMENTS
  - Active users see only their own private data: unchanged own-row
    policies + uid-prefixed storage (10.2, 9.2).
  - A deleted user loses access: auth.admin.deleteUser destroys the user
    row -> refresh tokens die immediately; any not-yet-expired access
    token (<= 1h) finds NOTHING to read because every row it could match
    has cascaded and every file under its prefix is swept (P5). Residual
    exposure is a token with zero readable rows (risk R6).
  - Retained assets never become public: deny-all RLS (10.1) + no
    authenticated storage policy on `retained/` (9.2/9.4) + application
    code never signs retained paths (7.3). Three independent layers,
    each sufficient alone.
  - Server-side/admin flows where required: the deletion endpoint runs on
    the service role (deleteUser, sweep, Zone B writes); cooldown
    enforcement lives in the DB trigger; character/quota RPCs keep their
    current SECURITY DEFINER design.
  - Nothing is weakened: the ONLY grant changes in this plan are one
    REVOCATION (M4) and brand-new deny-all tables.

10.4 SECURITY DEFINER CONSEQUENCES TO WATCH
  - Every new definer function sets `search_path = ''` and fully qualifies
    references (house style: 0001/0011/0016).
  - enforce_email_cooldown() executes on EVERY auth.users insert/update:
    exactly one PK-indexed lookup, raising ONLY the cooldown exception;
    the lookup is guarded so an unexpected error cannot take down
    unrelated auth writes (test S7).
  - The deletion endpoint re-verifies identity (Bearer session + password
    re-entry) before any destructive step and NEVER accepts a target uid
    from the client — always the session's own uid.

15. RISKS
================================================================================
 R1  TRIGGER PRIVILEGE UNKNOWN — whether BEFORE triggers on auth.users
     (and UPDATE OF email) are permitted must be proven in M0 on a
     staging clone; the standard Supabase pattern (AFTER INSERT
     handle_new_user) suggests yes. FALLBACK if not: Auth "Before User
     Created" hook (8.2b) — recorded as an explicit decision, never a
     silent weakening. Mitigation: M0 gates M2.
 R2  GENERIC ERROR UX — a trigger exception surfaces through GoTrue as a
     generic "Database error saving new user". Mitigation: optional
     signup-status pre-check (8.4) gives friendly copy while the trigger
     stays authoritative. Not a correctness risk.
 R3  DELETION CRASH WINDOWS — a crash between phases could leave partial
     state. Mitigated by: copy BEFORE delete (P2), cooldown BEFORE auth
     delete (P3 < P4), an idempotent phase machine in
     account_deletions, a retryable endpoint and verification (P6).
     Residual: retained copy done but auth delete failed -> retry; the
     ordering makes data loss impossible.
 R4  STORAGE COPY SIZE — many/large images make P2 long. Mitigation:
     pagination, per-file verification, ABORT BEFORE deletion on any
     failure; endpoint timeout leaves a resumable phase.
 R5  COOLDOWN HASH WEAKNESS — sha256(email) without salt is
     brute-forceable IF an attacker already reads the table; the table
     is deny-all to all clients and only the definer function reads it,
     so exposure requires a full DB compromise (which would already
     expose auth.users). Alternative (raw email, same protections)
     trades PII for readability — digest chosen. Documented, accepted.
 R6  TOKEN LIFETIME — a deleted user's access token stays valid until
     natural expiry (<= 1h) but matches zero rows (full cascade + sweep)
     so it can read nothing. Instant revocation would require shortening
     JWT expiry or a deny-list — explicitly NOT part of this plan.
 R7  DUAL WORLDS — retained files share a bucket with active files.
     Mitigation: prefix isolation + policy verification (M0/M5) +
     dedicated-bucket fallback; T-S4 proves it. If M0 finds a bucket-wide
     read policy, M5 becomes MANDATORY before M6 ships.
 R8  RETENTION/PRIVACY — retained images include a generated likeness
     (character models) because the requirement mandates preserving them.
     Mitigation: identity fully severed (no email/name/uid link),
     deny-all access, documented admin purge (delete account_deletions ->
     cascades rows, then delete retained files) for legal erasure.
     Decision recorded, not silent.
 R9  HISTORICAL ORPHANS — pre-existing orphan files (audit P3) are
     untouched; the T-EX3 baseline prevents confusing them with new leaks.
 R10 MIGRATION ORDERING — deleted_emails (M2) references
     account_deletions (M2, same file); retained tables (M3) reference
     account_deletions (M2). Sequence M2 -> M3 mandatory; each migration
     re-checks dependencies with guards.
 R11 EMAIL ALIASES — plus-addressing/dots are distinct strings to GoTrue;
     the cooldown digests exactly what GoTrue stores, so blocking
     behaves identically to today's uniqueness — no stronger, no weaker.
 R12 RACING SIGNUP DURING DELETION — a signup racing P4 hits native
     uniqueness (row present) or the cooldown (row present from P3);
     both reject safely; no partial state is reachable.
