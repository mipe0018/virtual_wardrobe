1. AUTHENTICATION
================================================================================
1.1 How users are created [C-CODE]
  src/pages/signup.astro:149-158 calls
    supabase.auth.signUp({ email, password, options: { data: { name, gender } } })
  `name` and `gender` are stored in auth.users.raw_user_meta_data only.
  Supabase errors are mapped at signup.astro:160-182; `user_already_exists`
  / "already registered" is shown as "An account with this email already
  exists. Try logging in instead." (lines 164-169).

1.2 How users log in [C-CODE]
  src/pages/login.astro:128 supabase.auth.signInWithPassword(...).
  Sessions are read via supabase.auth.getSession(); API routes authenticate
  the Bearer token through authenticateSupabaseRequest
  (src/lib/server/supabase.ts) returning { client, user } where `client` is a
  per-user anon-key client (RLS applies as that user). A separate
  createSupabaseServiceClient() uses SUPABASE_SERVICE_ROLE_KEY for trusted
  server work (supabase.ts:19-31).

1.3 auth.users <-> application records [C-CODE][C-MIGRATION]
  auth.users.id is THE user identifier everywhere:
  profiles.user_id, dressed_characters.user_id, wardrobe_items.user_id,
  wardrobe_results.user_id, wardrobe_item_ai_assets.user_id (+ legacy),
  ai_generation_usage.user_id, ai_generation_limit_overrides.user_id.
  Storage paths are also keyed by the auth uid as first segment
  (`${userId}/...`), with CHECK constraints split_part(path,'/',1)=user_id
  on wardrobe_items paths (0001:174-176, 0002:20-25, 0005:16-21) and on
  wardrobe_item_ai_assets.reference_path (0002:45-46, 0010:43).
  Composite keys (user_id, id) let child tables reference parents without
  cross-user leakage (dressed_characters, wardrobe_items, wardrobe_results,
  saved_dressed_outfits all PK (user_id, id)).

1.4 How profiles are created [C-CODE]
  NO database trigger and NO server endpoint inserts into `profiles` in this
  repository. The row is created lazily by the CLIENT:
    src/pages/profile.astro:633-646 — if the select returns no row on profile
    load, the page INSERTs { user_id, name, gender } from auth user_metadata
    (name falls back to the email prefix).
  The `profiles` table PREDATES all repo migrations: 202610040001:3 states
  "source_photo_path, model_photo_path, and model_generation_status already
  exist on profiles"; it only ALTERs the table (adds `gender`, check
  constraint and the gender-lock trigger, lines 5-39).
  => CREATE TABLE, RLS policies and any auth trigger for `profiles` are NOT
     in the repository [UNKNOWN — must be read from the live database].
     Provable: the client can SELECT/INSERT(when missing)/UPDATE its own
     profile row, so own-row policies must exist [INFERENCE from C-CODE].

1.5 Profile gender lock [C-MIGRATION]
  trigger profiles_gender_is_locked (0001:36-39) raises on UPDATE when
  old.gender IS NOT NULL and new.gender differs. First set is allowed
  (profile.astro:674/861, or at creation 633-646). Gender — and therefore
  base type — is immutable afterwards.

1.6 Deleting a profile vs deleting an Auth user [C-CODE]
  * The app contains NO code that deletes a `profiles` row and NO code that
    deletes an auth user (no auth.admin.deleteUser in src/; the only
    auth.admin call in the repo is scripts/set-owner.mjs, which only updates
    app_metadata.is_owner).
  * "Deleting the profile" can therefore only happen outside the app
    (dashboard / SQL console).
  * Deleting a profiles row does NOT delete auth.users and does NOT delete
    characters, items, assets, outfits or storage — none of them reference
    `profiles`; all reference auth.users. [C-MIGRATION]
  * Deleting an auth.users row WOULD cascade most tables (section 4), but
    storage files have no DB-side deletion. [C-MIGRATION][C-CODE]

1.7 THE "USER ALREADY EXISTS" PROBLEM — exact cause
  1. The app offers no account-deletion path; whatever deleted "the
     profile" could not have removed the auth.users row [C-CODE].
  2. supabase.auth.signUp() enforces email uniqueness in auth.users; the
     surviving (possibly unconfirmed) auth row makes signUp fail with
     `user_already_exists` / "already registered" [C-CODE — this exact
     error is matched at signup.astro:164-169].
  3. The UI shows "An account with this email already exists. Try logging
     in instead." (signup.astro:169).
  ROOT CAUSE in one sentence: PROFILE DELETION IS NOT ACCOUNT DELETION —
  `profiles` is a soft application record with no cascade to auth.users,
  while signup uniqueness lives entirely in auth.users, which nothing in the
  system ever deletes. [CONFIRMED BY CODE]
  Contributing facts [C-CODE]:
   - There is no /api/profile DELETE and no auth.admin.deleteUser call, so
     users cannot delete their own account from the product at all.
   - A dashboard deletion of only the profile row leaves auth.users AND all
     DRESSED data intact: the old account can still log in, and the profile
     row silently RE-INSERTS on the next /profile visit
     (profile.astro:633-646) — while remaining permanently blocked from
     re-signup with that email.
   - An earlier never-confirmed signup also leaves a pending auth.users row
     that blocks re-signup the same way [POSSIBLE PROBLEM — depends on the
     project's email-confirmation setting, UNKNOWN from the repo].

3. USER OWNERSHIP
================================================================================
3.1 Direct vs indirect ownership
  DIRECTLY owned by the user (user_id -> auth.users ON DELETE CASCADE):
    dressed_characters, wardrobe_items, wardrobe_results,
    wardrobe_item_ai_assets (current), ai_generation_usage,
    ai_generation_limit_overrides. [C-MIGRATION]
  OWNED TRANSITIVELY (no direct auth FK; cascade through a parent):
    wardrobe_item_ai_assets_legacy (via wardrobe_items and
      dressed_characters — 0002:36-44)
    saved_dressed_outfits          (via dressed_characters — 0012:31-33)
  NOT user-owned (global reference): dressed_base_forms,
    ai_generation_limits. [C-MIGRATION]
  UNKNOWN: profiles (definition predates the repo).

3.2 Chain 1 — USER -> PROFILE -> CHARACTER -> PERSONAL MODEL [C-CODE]
  auth.uid -> profiles.user_id (client-created row, profile.astro:633-646)
           -> dressed_characters.user_id (row created ONLY by the
              publish_dressed_character RPC, which requires
              profiles.gender = p_gender — 0001:94-100 / 0012:216-223)
           -> personal model = dressed_characters.model_path, a FILE in
              bucket `model-images` at `{userId}/personal-model-{uuid}.png`
              (character-job.ts:119), mirrored to profiles.model_photo_path
              by the same RPC (0012:238-244).
  The character row belongs to the user directly; the model file's storage
  owner is the uploader and its DB reference is guarded by CHECK
  split_part(model_path,1)=user_id (0001:49-50).

3.3 Chain 2 — USER -> WARDROBE ITEM -> CLOTHING ASSET [C-CODE][C-MIGRATION]
  auth.uid -> wardrobe_items.user_id (row created by POST
              /api/wardrobe/items, items/index.ts:441-460)
           -> wardrobe_item_ai_assets (user_id, item_id) — written ONLY by
              the service role inside runClothingJob
              (clothing-job.ts:185-198, upsert on
              (user_id,item_id,base_type))
           -> asset file in `model-images` at
              `{userId}/clothing/{characterId}/{uuid}.png`
              (clothing-job.ts:170-171). The FOLDER is named after the
              character primary at generation time, but the ROW is keyed by
              base_type, not by character.
  The asset row belongs to the user directly; it depends on the item
  (FK cascade) but NOT on any character row.

3.4 Chain 3 — CHARACTER -> SAVED OUTFIT [C-MIGRATION]
  dressed_characters (user_id,id) -> saved_dressed_outfits
  (user_id,character_id) ON DELETE CASCADE (0012:31-33): a saved outfit
  belongs to the user AND is bound to one character; deleting that character
  silently deletes the outfit row.
  saved_dressed_outfits.item_ids reference wardrobe_items only by VALUE
  (text[]); integrity is enforced solely by the item-delete trigger
  (0012:166-185), which deletes the WHOLE outfit when any listed item dies.

4. ACCOUNT DELETION
================================================================================
4.1 The event: auth.users row is deleted
  There is NO application path for this [C-CODE]; it can only happen via the
  Supabase dashboard / Admin API. IF it happens, the DB consequences are:

  Record                                   | Fate on auth delete | Source
  -----------------------------------------+---------------------+---------
  profiles row                             | UNKNOWN (not in repo)
  dressed_characters                       | CASCADE delete      | 0001:42
  wardrobe_items                           | CASCADE delete      | 0001:170
  wardrobe_results                         | CASCADE delete      | 0001:217
  wardrobe_item_ai_assets (current)        | CASCADE delete      | 0010:32
  wardrobe_item_ai_assets_legacy           | cascade (transitive)| 0002:36-44
  saved_dressed_outfits                    | cascade (transitive)| 0012:31-33
  ai_generation_usage                      | CASCADE delete      | 0001:258
  ai_generation_limit_overrides            | CASCADE delete      | 202610050001:17
  dressed_base_forms / ai_generation_limits| untouched (global)
  All STORAGE files under {userId}/...     | NOT TOUCHED         | [no code]
  [CONFIRMED BY MIGRATION for rows; CONFIRMED BY CODE for storage]

  => ACCOUNT DELETION LEAVES EVERY STORAGE FILE ORPHANED: source photos
     (profile-images), personal models, clothing originals, previews,
     AI-ready layers, try-on results and outfit results all survive in the
     `model-images` / `profile-images` buckets with no owning row.
     [CONFIRMED BY CODE — no storage.remove() is ever tied to auth deletion]

4.2 Per-asset detail (what a cascade does NOT reach)
  * Original clothing images (item.original_path), previews
    (item.preview_path), legacy reference_path files: their DB rows vanish
    with wardrobe_items, but the FILES persist. [C-MIGRATION + C-CODE]
  * AI-ready reusable clothing assets: rows vanish via FK cascade; FILES
    under {userId}/clothing/{characterId}/ persist. [same]
  * Saved outfits: rows vanish transitively; they hold no files.
    [C-MIGRATION]
  * AI usage / overrides: rows vanish (quota history dies with the user).
    [C-MIGRATION]
  * wardrobe_results files under {userId}/wardrobe-results/ persist.
    [C-CODE]

4.3 The opposite event: only the application profile row is deleted
  The app cannot do this; assume a dashboard/SQL delete of `profiles`.
  [C-CODE]
  What REMAINS [C-MIGRATION]:
    - auth.users row (email still registered -> cannot re-signup)
    - every dressed_characters row (primary flag untouched)
    - every wardrobe_item, asset, result, saved outfit, usage row
    - every storage file
  What BREAKS or behaves oddly [C-CODE][LIKELY PROBLEM]:
    - publish_dressed_character requires a matching profile row
      (0001:94-100 / 0012:216-223) -> NEW character generation fails with
      "The character model type does not match the locked profile type."
    - set_primary_dressed_character joins profiles (0001:135-140) -> the
      profile.model_photo_path update silently no-ops.
    - delete_dressed_character updates profiles conditionally -> degrades
      silently (guarded WHERE).
    - The profile page RE-CREATES the row on next visit
      (profile.astro:633-646), restoring name/gender from auth metadata —
      but source_photo_path / model_photo_path / model_generation_status
      return NULL while the old characters and files still exist
      [LIKELY PROBLEM: profile and character state desynchronise].
  Relationships preventing deletion: NONE reference `profiles` — nothing
  cascades from it and nothing except the RPCs depends on its presence.

4.4 Orphan inventory (both events combined) [CONFIRMED BY CODE]
  Orphaned DATABASE rows: none reachable through the application's own
  delete flows — every delete path goes through tables with FK cascades or
  SECURITY DEFINER RPCs that clean dependants. [C-CODE] The only DB-side
  orphan risk is rows whose parents are deleted by a process outside the
  app (e.g. raw SQL) in a way that bypasses FKs — not demonstrated.
  Orphaned STORAGE files (the real gap):
    - ALL user files on account deletion (4.1/4.2)
    - {userId}/clothing/{A}/... files kept on purpose when character A was
      deleted while its base type stayed covered (characters/[id].ts:125-132)
      are never revisited later: when the covering character B is finally
      deleted, the cleanup query is scoped to B's folder only
      (characters/[id].ts:109-114), so A's folder remains forever
      [CONFIRMED BY CODE]
    - a background function killed between storage upload and DB upsert
      (clothing-job.ts:170-199) leaves an unlinked PNG
      [POSSIBLE PROBLEM — cleanup exists only in catch/finally]
    - items/index.ts deletes originals/previews/assets/results on item
      delete (lines 85-131) — good; failures there return 500 but the DB row
      is already gone, leaving files [POSSIBLE PROBLEM]
  Records that remain unexpectedly:
    - profiles survives every "user deleted their stuff" operation short of
      an auth delete (section 1.7); model_generation_status persists with no
      job history.
  Relationships that prevent deletion (intentional guards):
    - api/characters/[id].ts:70-72 refuses to delete the LAST character
      (409); :83-88 refuses to delete the primary without a normalized
      same-gender replacement.

4.5 Character deletion detail [C-CODE + C-MIGRATION]
  DELETE /api/characters/{id} -> rpc delete_dressed_character
  (0010:103-193) + storage cleanup in characters/[id].ts:
   - nulls wardrobe_items.reference_path that pointed at legacy asset paths
   - deletes wardrobe_results for the character (FK also cascades)
   - deletes wardrobe_item_ai_assets_legacy rows (FK also cascades)
   - promotes a replacement primary + updates profiles.model_photo_path
   - deletes the dressed_characters row
  Storage removal (characters/[id].ts:134-139,202-218):
   - character.model_path, legacy asset paths, result paths
   - ACTIVE base-type asset files under {userId}/clothing/{characterId}/
     ONLY when no other normalized character of the same gender remains
     (baseTypeStillCovered, lines 125-132), after which the matching asset
     ROWS are also deleted (lines 188-200).
  => Deleting a character CAN delete reusable clothing assets — but only
     when it is the LAST normalized character of that base type, i.e.
     precisely when the app can no longer use them. [CONFIRMED BY CODE]
     Files under ALREADY-deleted characters' folders are outside this
     query's scope and survive (see 4.4). [CONFIRMED BY CODE]

5. CLOTHING ASSET ARCHITECTURE (CURRENT IMPLEMENTATION)

5.1 What identifies a wardrobe item [C-MIGRATION][C-CODE]
  Composite PK (user_id, id), where `id` is application-generated text
  (items/index.ts:441-460 creates the row); unique only within a user.
  Storage identity: original_path / preview_path / legacy reference_path,
  each CHECKed to start with the owner's uid.

5.2 What identifies a clothing asset [C-MIGRATION 0010:31-44]
  Composite PK (user_id, item_id, base_type) with generation_version > 0.
  Exactly ONE row per (item, base type); regeneration UPSERTS over it
  (clothing-job.ts:185-194). The image is a private storage file at
  `{userId}/clothing/{characterIdWhenGenerated}/{uuid}.png`.

5.3 Item <-> asset relationship [C-MIGRATION]
  FK (user_id, item_id) -> wardrobe_items(user_id,id) ON DELETE CASCADE.
  One item -> 0..2 current assets (one per base type), plus 0..n frozen
  legacy rows in wardrobe_item_ai_assets_legacy (character-bound).

5.4 How base_type is used [C-CODE]
  * Generation: process-clothing.ts:281-291 requires baseType to equal the
    primary character's gender; the asset row stores it.
  * Listing: items/index.ts:238-311 returns aiReadyAssets keyed by
    base_type; "AI READY" requires baseType == primary gender AND
    generation_version == CURRENT_CLOTHING_ASSET_VERSION (3).
  * Rendering: wardrobe.astro:209 / profile-outfits.ts:27 select
    aiReadyAssets[baseType] only; save_dressed_outfit (0014:74-87) rejects
    outfits whose items lack a current (v3) asset for the active base_type.

5.5 Assets and characters [C-CODE]
  CURRENT asset rows are NOT linked to any character. The only character
  link is the folder inside reference_path
  (`{userId}/clothing/{characterId}/`) — purely historical. Compatibility
  is the app-level rule "asset base_type == primary character's gender",
  not a FK. [CONFIRMED BY CODE]

5.6 Can the same asset be reused? Is it actually shared? [C-CODE][C-MIGRATION]
  - Across outfits and across characters OF THE SAME BASE TYPE: YES — one
    row serves every composition; saving many outfits reuses the same
    reference_path (outfits/index.ts:117 checks existence, does not copy).
  - Across characters of DIFFERENT base types: NO — a second asset must be
    generated per base_type (PK enforces one per base type).
  - Across users: NO — user_id is in the PK, RLS restricts to
    auth.uid() = user_id, and the path CHECK forbids pointing at another
    user's folder. There is NO sharing mechanism at all.
    [CONFIRMED BY CODE]
  => "Reusable" in DRESSED means reusable within ONE user across
     characters/outfits/regenerations — NOT a shared catalogue.

5.7 Can deleting a character accidentally delete reusable clothing?
  YES, in exactly one scoped case [C-CODE]:
   - If the deleted character is the LAST normalized character of its base
     type, characters/[id].ts:125-132 + 188-200 delete BOTH the asset rows
     (by reference_path prefix) and the files. Without any such character
     the fitting room cannot render them anyway, but the loss is permanent:
     re-creating a character later finds no assets and must regenerate
     (spending quota).
   - If another normalized character of the same base type remains, rows and
     files are kept (baseTypeStillCovered) — reuse preserved. [C-CODE]
   - CAVEAT: cleanup only matches the JUST-deleted character's folder;
     rows/files created under earlier, already-deleted characters are never
     removed — a leak in the opposite direction. [CONFIRMED BY CODE]

5.8 Can deleting a wardrobe item accidentally delete an asset used elsewhere?
  The asset FK cascades from wardrobe_items, so deleting the item deletes
  BOTH of its base-type asset rows; items/[id].ts:85-131 additionally
  deletes their storage files plus related wardrobe_results.
  Because assets are per-item (never shared BETWEEN items), no other item's
  asset is affected. [CONFIRMED BY CODE][C-MIGRATION]
  Collateral damage: any saved_dressed_outfits row containing the deleted
  item is deleted WHOLE by the trigger (0012:166-185) — never edited.
  [CONFIRMED BY MIGRATION]

5.9 Two generations of asset tables coexist [C-MIGRATION]
  wardrobe_item_ai_assets_legacy (character-bound, 0002) and
  wardrobe_item_ai_assets (base-type, 0010). Every delete path must handle
  both (items/[id].ts:55-92, characters/[id].ts:92-115) — and does. Reads
  use only the current table (plus the legacy reference_path column on
  wardrobe_items). [C-CODE]

================================================================================

8.1 What DRESSED reads from Supabase [C-CODE]
  GET /api/wardrobe/items (items/index.ts:160-343):
    - dressed_characters (primary row: id, gender, model_path,
      geometry_contract_version)
    - wardrobe_items (own rows), wardrobe_item_ai_assets (base-type rows),
      wardrobe_results (legacy cleanup paths)
    - storage signed URLs for every referenced path
  wardrobe.astro:276-387 additionally reads `profiles` (gender,
  source_photo_path, model_photo_path) and dressed_characters from the
  browser; saved outfits come from GET /api/wardrobe/outfits (index.ts:34)
  and are saved via rpc save_dressed_outfit (index.ts:138).

8.2 Which IDs it uses [C-CODE]
  - primary character: dressed_characters.id (uuid), gated on
    geometry_contract_version = 'normalized-v1' (wardrobe.astro:302-309;
    outfits/index.ts:108-112; items/index.ts:343-346)
  - items: wardrobe_items.id (text)
  - assets: (user_id, item_id, base_type), selected client-side with
    baseType = primary character gender
  - outfit: saved_dressed_outfits.id (uuid), unique per
    (user, character, outfit_key)

8.3 Are clothing references stable? [C-CODE][C-MIGRATION]
  YES at row level: the asset PK never changes and regeneration upserts in
  place. `reference_path` may change (new uuid file, old file deleted) but
  every consumer re-reads the row on each load and receives a fresh signed
  URL (items/index.ts:216-311).
  Saved outfits store item_ids, NOT paths — a regenerated asset is picked
  up automatically; a BUMPED generation version (CURRENT=3) hides items
  until regenerated (render filter wardrobe.astro:211-214) while the saved
  outfit row survives intact.

8.4 Do saved outfits reference reusable clothing assets? [C-CODE]
  Indirectly: saved_dressed_outfits.item_ids -> wardrobe_items.id ->
  wardrobe_item_ai_assets[base_type] resolved at render time. They never
  copy the asset. save_dressed_outfit REQUIRES every item to own a
  version-3 asset for the active base_type (0014:74-87).

8.5 Can deleting something break an existing saved outfit?
  [C-MIGRATION][C-CODE]
  - Delete the OUTFIT row: nothing else affected (no files).
  - Delete a WARDROBE ITEM: the trigger removes EVERY saved outfit
    containing it (0012:166-185) — whole-outfit deletion, silently.
    [LIKELY PROBLEM from UX; integrity-preserving]
  - Delete a CHARACTER: FK cascade silently deletes ALL saved outfits bound
    to it (0012:31-33). [CONFIRMED BY MIGRATION]
  - Regenerate/invalidate an asset: outfit survives; rendering filters the
    item out until a current asset exists (8.3). [C-CODE]
  - Delete the account: everything above cascades away except storage.

9.5 Failed / cancelled / abandoned — orphan analysis [CONFIRMED BY CODE]
  Character:
   - normal failure paths delete the uploaded file
     (character-job.ts:154-159) and mark status failed. If the function is
     KILLED mid-run, the file can survive unlinked [POSSIBLE PROBLEM] and
     the lock stays until the next reserve clears it after the 5-minute
     window (0015:41-52) — but used_count (incremented at reserve) is NEVER
     credited back because finalization never runs [LIKELY PROBLEM: an
     abandoned character generation permanently burns quota out of a limit

     permanently consumes quota, unlike the background character path
     (0016 credits back). [CONFIRMED BY CODE — asymmetry]
  Cancelled: no cancellation mechanism exists (only 5-minute stale-lock
  recovery). [CONFIRMED BY CODE]

11.3 Automatic deletion? [C-CODE]
  NO storage triggers/lifecycle rules exist in the repository, and Supabase
  storage does not cascade from SQL. Deletion is purely
  APPLICATION-INITIATED:
   - item delete        -> items/[id].ts:120-131 (original, preview,
                           legacy reference, BOTH asset files, results)
   - character delete   -> characters/[id].ts:202-218 (model, legacy

   - clothing regen     -> clothing-job.ts:200-213 (replaced file),

   - try-on failure     -> try-on.ts:247-266 (partial file)
   - ACCOUNT deletion   -> NOTHING (no code path exists)
  => DB deletion NEVER removes storage by itself. [CONFIRMED BY CODE]

11.4 Can storage files become orphaned? [CONFIRMED BY CODE]
  YES, four documented ways:
   A. Account deletion: every user file remains.
   B. Character-folder leftovers: files kept under an earlier deleted
      character's folder are never revisited by later cleanups (4.4).
   C. Crash between upload and DB write (background clothing/character
      jobs; item upload dying between items/index.ts:429 and 441-460).
   D. storage.remove() failing after a successful DB delete (item delete
      returns 500 with the row already gone — items/[id].ts:124-130).
  Plus BENEVOLENT orphans kept on purpose for reuse (active assets whose
  character is gone but whose base type is still covered).

11.5 What should logically be deleted with a user/account [analysis]
  Everything under `{uid}/` in BOTH buckets: source photo, personal models,
  clothing originals, previews, AI-ready layers, try-on and result images.
  NOT to be deleted with a user: `system-reference/base-forms/*` (shared
  platform data registered in dressed_base_forms). User-owned prefixes are
  `{uid}/`; shared/reference files live under `system-reference/` with no
  uid. Nothing else in storage is shared today (5.6: assets are never
  cross-user). [CONFIRMED BY CODE]

15. CURRENT VS INTENDED ARCHITECTURE
================================================================================
Intended:
  USER
  ├── PROFILE └── CHARACTER └── PERSONAL MODEL
  ├── CLOSET └── WARDROBE ITEM └── REUSABLE CLOTHING ASSET
  └── DRESSED └── SAVED OUTFITS
  CHARACTER -> BASE TYPE -> COMPATIBLE CLOTHING ASSETS
  AI -> CHARACTER GENERATION | CLOTHING GENERATION | TRY-ON | QUOTA/USAGE

Meaningful differences found (current vs intended):

 D1. REUSABLE ASSET DEPENDS ON ITEM, NOT ON CHARACTER — ALIGNED.
     Asset PK (user, item, base_type); characters only gate by gender.
     Matches "CHARACTER -> BASE TYPE -> COMPATIBLE ASSETS". [C-CODE]
 D2. NO CROSS-USER SHARING — "reusable" is implemented only WITHIN a user
     (5.6). If a shared catalogue was meant, it does not exist. [C-CODE]
 D3. PERSONAL MODEL FILE IS DOUBLE-REFERENCED — character.model_path is
     authoritative, but profiles.model_photo_path duplicates it and is
     maintained by three different RPCs; deleting the profile breaks the
     mirror (4.3). The intended tree is one-directional. [C-CODE]
 D4. SAVED OUTFITS ARE CHARACTER-BOUND — the intended tree hangs them off
     DRESSED under USER; current schema hangs them off the CHARACTER with
     cascade (2.7), so deleting a character silently destroys outfits.
     [C-MIGRATION]
 D5. ASSET FILES ARE CHARACTER-NAMED — storage paths embed a characterId
     although rows are base-type keyed (5.5). Works, but couples storage
     layout to a deletable entity and creates orphans (4.4, 11.4). [C-CODE]
 D6. NO AI GENERATION ENTITY — the intended AI section reads like
     first-class generation records; current has only counters + results,
     so history/retry/audit are impossible (2.13). [C-CODE]
 D7. QUOTA SEMANTICS ARE INCONSISTENT across the three generation types
     (10.4/10.5); intended behaviour is presumably uniform. [C-CODE]
 D8. ACCOUNT LIFECYCLE MISSING ENTIRELY — no deletion path, no profile
     delete, storage never follows the DB (sections 1, 4, 11). [C-CODE]
 D9. TWO ASSET GENERATIONS COEXIST (legacy + current) — a migration
     artefact invisible in the intended design. [C-MIGRATION]
 D10. TRY-ON EXISTS TWICE (dress-model + fashn try-on), neither reachable
     from the UI (only /api/ai/{personal-model,process-clothing,usage} are
     called by client code) — the intended AI section lists TRY-ON as
     active; current wiring is ambiguous. [C-CODE][UNKNOWN]

17. TARGET DATABASE ARCHITECTURE
================================================================================
Principle: smallest safe changes; preserve stable IDs; keep user-private
data separate from shared/reusable data; make deletion deterministic.

17.1 Authentication
  - Keep Supabase Auth as the only identity source; keep auth.uid() as the
    single user id used by every table and storage prefix. [no change]
  - ADD an explicit account-deletion path (server endpoint using the
    service role) that: deletes the auth.users row (cascades rows), then
    removes `{uid}/` prefixes in both buckets, then confirms zero orphans.
    This alone fixes F27: deleting an account releases the email.
  - OPTIONAL: a database trigger on auth.users INSERT that creates the
    profiles row (moving profile creation server-side), making the
    profile's existence independent of client code — smallest variant of
    the current insert-if-missing behaviour. [F02/F28]
17.2 Profiles
  - Bring the CREATE TABLE + RLS of `profiles` into version control (they
    exist only in the live DB today — F37). Keep own-row SELECT/INSERT/
    UPDATE, no client DELETE.
  - Keep gender lock; document that profiles is a projection of auth
    metadata + pointers (model_photo_path stays a mirror of the primary
    character; the RPCs already maintain it).
17.3 Characters
  - Keep dressed_characters exactly as-is (PK, cascade, one-primary index,
    contract version, definer RPCs) — it is the best-shaped table in the
    schema.
  - Extend delete_dressed_character's storage cleanup to sweep ALL
    `{uid}/clothing/%` folders for base types that lose their last
    normalized character (fixes F04) instead of only the current
    character's folder.
17.4 Wardrobe items
  - Unchanged (PK, cascades, path CHECKs, RLS).
  - Keep the saved-outfit trigger, but change its behaviour to REMOVE the
    dead item_id from item_ids and delete the outfit ONLY when fewer than 1
    item remains (small trigger change; fixes F32 without losing outfits).
17.5 Reusable clothing assets (KEY DECISION)
  - Keep PK (user, item, base_type) and service-role-only writes.
  - DROP the client DELETE grant (F08): deletion should happen only via
    item cascade or an explicit server endpoint that also removes the file.
  - Rename the storage folder away from characterId for NEW assets, e.g.
    `{uid}/clothing-assets/{item_id}-{base_type}-{uuid}.png`, so storage
    no longer depends on a deletable entity (D5). Old paths keep working —
    reference_path is opaque (8.3).
  - Keep base_type as the compatibility key; characters continue to gate
    by gender. This preserves the intended
    CHARACTER -> BASE TYPE -> COMPATIBLE ASSETS relation without FKs.
17.6 Saved outfits
  - Keep (user_id, id) + character FK, or (smaller change) make character
    ON DELETE SET NULL and drop the NOT NULL so outfits survive character
    deletion — only if product wants that; otherwise keep cascade and
    document it. [choose one; recommend documenting first]
  - Add a generated/derived column for base_type already present — keep.
17.7 AI generations (optional, later)
  - Optional audit table ai_generation_events (id, user_id, type, status,
    started_at, finished_at, error) written ONLY by server code — solves
    F29/F30 debugging without touching quota logic.
17.8 Quotas
  - Keep tables; unify semantics: either count-at-reserve + refund (all
    types) or count-at-success (all types). Smallest fix: make the sync
    try-on routes call the SERVER finalizer (finish_ai_generation_server)
    so failures refund (fixes F30) — one call-site change per route.
  - Move the seeded override row out of the migration into an ops script
    (F31) in a later migration that only deletes/reseeds deliberately.
17.9 Storage
  - Keep the two buckets and uid prefixes (they already encode ownership).
  - Add a documented deletion order: rows first (within a transaction),
    storage second, with idempotent retries (fixes F34/F35 patterns).
17.10 RLS
  - Keep the definer-RPC pattern; it is the right model.
  - Revise: asset DELETE (17.5); consider revoking legacy-table INSERT/
    UPDATE (read-only preservation, 12.5).
  - Bring profiles + storage policies under migration control (17.1/17.9).
17.11 Account deletion (target)
  - See section 18 (dedicated target).

18. ACCOUNT DELETION TARGET
================================================================================
Classification first — two clearly different classes:

  USER-OWNED DATA (must disappear with the account):
    profiles row; dressed_characters rows + personal-model PNGs;
    wardrobe_items rows + clothing-originals + clothing-previews;
    wardrobe_item_ai_assets rows + their PNGs (unless see REUSABLE);
    wardrobe_item_ai_assets_legacy rows; saved_dressed_outfits rows;
    wardrobe_results rows + result PNGs; try-on PNGs;
    ai_generation_usage rows; ai_generation_limit_overrides row;
    the source photo; EVERY storage object under `{uid}/` in both buckets.

  REUSABLE / SHARED DATA (must NOT be destroyed by anything except the
  account owner's own deletion of their only copy):
    - Within the current architecture, the "reusable clothing asset" is
      USER-SCOPED (5.6): it is only "shared" between the user's own
      characters/outfits. => on ACCOUNT deletion it MUST be deleted with
      the account (it is private data), and that does not violate reuse.
    - Platform-shared data: dressed_base_forms rows and the two
      system-reference/base-forms/*.png files — NEVER deleted with a user.
    - If cross-user sharing is added later (a global catalogue), those
      rows/files must move OUT of `{uid}/` prefixes and out of per-user FKs
      BEFORE any deletion logic is written (17.5).

 E1. USER DELETES ACCOUNT (new endpoint, service role):

19. RLS TARGET
================================================================================
Guarantees the model must provide:

 1. A user can only ever SELECT/INSERT/UPDATE/DELETE rows where
    user_id = auth.uid() — already true for every table in the repo
    (12.1-12.9); must be made true for `profiles` by bringing its policies
    under version control (17.2).
 2. Users can never write quota, override, or cross-user tables — already
    true (12.7-12.9); keep zero policies on
    ai_generation_limit_overrides.
 3. Asset rows are written only by trusted server code — keep
    service_role-only INSERT/UPDATE; REMOVE the client DELETE (17.5) so a
    client cannot delete a row whose file it will not remove.
 4. All privileged mutations flow through SECURITY DEFINER RPCs that
    re-derive auth.uid() internally (publish/set_primary/delete character,
    save outfit, reserve/finalize quota) — keep and prefer this pattern
    over new table grants.
 5. Storage mirrors RLS: authenticated users may read/list/upload/delete
    ONLY objects under `{uid}/`, plus READ-ONLY access to the two
    system-reference base-form files (0010 policy). These bucket policies
    must be captured as SQL in a future migration (F36) so they are
    reviewable and reproducible.
 6. Reusable assets and future shared data:
    - today: reusable assets are private -> own-row SELECT is correct and
      sufficient; NO cross-user SELECT should be added while assets live
      under `{uid}/`.
    - if a shared catalogue is ever introduced: put shared rows in a table
      WITHOUT user_id (or with nullable owner) and grant SELECT to
      authenticated with using (true), while INSERT/UPDATE/DELETE stay
      service-role-only; shared FILES must live under a non-uid prefix
      (e.g. shared-assets/) with an authenticated SELECT-only policy.
    - rule of thumb: uid prefix in storage <=> user_id in table; anything
      shared must have NEITHER.
 7. Service role remains the only actor for finalization and cross-user
    admin (account deletion) — unchanged.

Do not implement any of this now; this is the target description only.

## CURRENT ARCHITECTURE
Supabase Auth (auth.uid() = the only user id) + a `profiles` projection
created client-side + DRESSED domain tables keyed by (user_id, ...) with
ON DELETE CASCADE from auth.users, written through SECURITY DEFINER RPCs
where integrity matters, guarded by per-user RLS, storing images in two
private uid-prefixed buckets, with quota counters (limits/usage/overrides)
reserved and finalized by definer functions (service-role finalization for
clothing). Reusable clothing = one asset row per (user, item, base_type)
referencing an opaque storage path; characters gate assets only by gender
base type. [CONFIRMED BY CODE / MIGRATION; `profiles` + storage policies
partly UNKNOWN]

## CONFIRMED PROBLEMS
 - No account deletion exists; profile deletion cannot free the email ->
   "user already exists" (F01/F27, section 1.7).
 - Storage never follows the DB: an auth delete orphans every file
   (F03, 4.1); the character-folder sweep misses previously deleted
   characters' folders (F04, 4.4).
 - Failed sync try-on and abandoned character jobs permanently consume
   quota (F05/F06/F29/F30).
 - Client holds DELETE on asset rows without file cleanup (F08, 12.4).
 - Deleting an item silently deletes whole saved outfits (F14/F32).
 - Test-account UUID seeded in a shipped migration (F18/F31).
 - Migrations 0003/0004/0006/0007/0009 are missing from the repo (F19).

## POSSIBLE PROBLEMS
 - Unconfirmed pending auth rows also block re-signup (F33).
 - Orphaned files when a process dies between upload and DB write (F34).
 - Orphaned files when storage.remove() fails after a row delete (F35).
 - Live bucket policies/lifecycle rules may differ from the repo
   (F36, F40).

## WHAT IS WORKING
 - Ownership enforcement: every repo table policy and API query is scoped
   to auth.uid(); path CHECKs mirror uid into storage paths (F12).
 - Row-level cascade integrity: account/character/item deletions clean up
   dependants correctly via FKs and RPCs (F13-F15).
 - Base-type reusable assets: one row per (item, base_type), reused across
   outfits and characters without copying (5.6, D1).
 - Quota plumbing: in-progress lock, 5-minute stale recovery, service-role
   clothing finalization, JWT-based owner exemption, deny-all override
   table (F16-F18, section 10).
 - Character model: one-primary index, gender lock, geometry-contract
   gating end-to-end (F20).
 - Item/character delete endpoints clean storage thoroughly for the paths
   they know about (items/[id].ts, characters/[id].ts).

## USER-ALREADY-EXISTS PROBLEM
Cause (CONFIRMED BY CODE): the app has no path that deletes auth.users;
whatever deleted "the profile" removed only the profiles row. Supabase
signup uniqueness lives in auth.users, so signUp fails with
user_already_exists and the UI shows "An account with this email already
exists" (signup.astro:164-169). The surviving auth user can still log in,
and the profile row silently re-creates itself on the next /profile visit —
while the email stays permanently unusable for a new signup.
Fix direction (NOT implemented): a real account-deletion flow (M2) that
deletes the auth user (cascading rows) and sweeps `{uid}/` storage; plus
optionally a server-side profile-creation trigger so profiles never drift.

## CLOTHING REUSABILITY
Current: reusable WITHIN one user across characters/outfits of the same
base type; never shared between users; keyed (user, item, base_type);
files under a character-named folder but character-independent rows.
Risks: last-character deletion removes those assets (scoped, arguably
intended); folders of earlier deleted characters leak (F04); client DELETE
can orphan files (F08); item deletion cascades assets (correct — they are
per-item). Hard rule: never delete an asset file while a row still
references it (section 18).

## ACCOUNT DELETION
No feature exists. Target: service-role endpoint -> delete auth.users
(cascades all rows, including profiles once verified) -> sweep `{uid}/` in
both buckets -> verify zero orphans -> email released. Character/item/
outfit rules as in section 18, with reverse-lookup protection for
reusable assets.

## STORAGE
Two private buckets; uid prefixes encode ownership; shared masters under
system-reference/. Deletion is 100% application-initiated; DB deletes never
touch files. Orphan classes: account deletion, character-folder leftovers,
mid-crash uploads, failed removes (11.4). Target layout and deletion order
in section 20; bucket policies should be captured as SQL.

## RLS
Consistent per-user model using the definer-RPC pattern; deny-all on
overrides; service-role-only asset writes. Gaps: `profiles` and user-folder
storage policies are outside the repo (UNKNOWN); client DELETE on assets is
too permissive; legacy table grants are redundant. Target guarantees in
section 19, including "uid prefix in storage <=> user_id in table; shared
objects have neither".

## QUOTA SYSTEM
Two coexisting counting philosophies (count-at-reserve vs
count-at-success) in one table; refunds work only on background paths;
overrides and owner exemption are correctly hardened. Fix direction:
unify finalization on the server finalizer (M6), add observability (M9),
remove the shipped test seed (M8).

## RECOMMENDED TARGET ARCHITECTURE
As section 17: keep auth.uid() as the single identity; version-control
profiles; keep characters/items/outfits schema as-is; keep base-type assets
with service-role writes but drop client DELETE; decouple asset storage
folders from characterId for new files; derive every deletion from a reverse
lookup of reference_path; add account deletion with a storage sweep; capture
storage policies as migrations; optionally add an ai_generation_events
audit table. All of it stays inside the existing PROFILE -> CLOSET ->
DRESSED structure.

## SMALLEST SAFE IMPLEMENTATION PLAN
M1 profiles into version control -> M2 account deletion + storage sweep
(fixes the reported user problem) -> M3 revoke asset client DELETE ->
M4 complete character storage sweep -> M6 try-on finalization unification
-> then optional M5/M7/M8/M9. Each step is small, additive or guarded,
independently testable with section 22, and committed to the repo BEFORE
being run anywhere (section 21).
