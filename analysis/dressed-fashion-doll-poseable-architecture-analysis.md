## Executive Summary

1. **DRESSED should adopt a stylized fashion-doll identity for its 3D body**
   (original design in the visual language of fashion mannequins/dolls — not a
   copy of any copyrighted character). The direction is technically sound and
   fits the Clueless-inspired aesthetic. (Recommendation; IP specifics
   UNVERIFIED — legal review before any public launch.)

2. **The correct foundation is a shared humanoid skeleton with a hybrid
   attachment model (Option D):** body-worn garments = **skinned to the same
   skeleton as the body**; accessories/shoes/hats/bags = **rigid, parented to
   anchor nodes on bones**; **no cloth simulation** — now or foreseeably.
   The "clothing sticks to the body" requirement is satisfied *by construction*:
   a garment is either weight-bound to bones (deforms) or parented to a bone
   (follows) — never manually repositioned per pose, never re-generated by AI.

3. **The skeleton is the foundation decision; everything else hangs off it.**
   ~22 bones (root, pelvis, spine, chest, neck, head, 2× clavicle/upperArm/
   lowerArm/hand/upperLeg/lowerLeg/foot) are sufficient for natural fashion
   poses, garment deformation, hair, accessories, and future full FK posing.
   Fingers, toes, twist bones, facial bones, IK, and helper/dynamics bones are
   **deferred with explicit trigger conditions** (§6).

4. **The current body (`dressed-base.glb`) is retained as the starting point**
   — but with one mandatory gate: it was procedurally built from *overlapping
   closed shells* (arm/leg/torso shells interpenetrate at shoulder/hip). This
   is the single biggest technical risk for rigging: separated weights across
   an interpenetration seam can tear visually when a limb rotates. Phase 2 rigs
   this exact GLB with computed auto-weights and **pose-tests it**; only if the
   seams fail does the body move to a Blender retopology pass (free, open
   source). No rebuild before evidence.

5. **Base pose: relaxed A-pose** (arms cleared ~30° from the torso — slightly
   wider than today's), symmetric, feet slightly apart. The fashion/display
   pose is a *runtime pose preset*, never baked into the bind pose. T-pose is
   not recommended as the master: it fights the doll silhouette and the
   arms-down 2D heritage, and buys only marginally easier shoulder weights that
   A-pose with clearances handles fine.

6. **AI stays out of the runtime entirely.** AI is used once per *unique
   garment asset* (reconstruction/classification, hash-gated, background job);
   posing, deformation, attachment, rotation, camera and rendering are 100 %
   deterministic CPU/GPU work on cached GLBs. Cost per user action ≈ 0 by
   construction — the architecture *is* the cost control.

7. **2D remains untouched.** Future `placement3d` is a lazy, NULL-default
   sibling column of `placement`; outfits already store `item_ids` only;
   selection (`editingItemId`) and gestures are renderer-neutral. 3D ships
   additive behind the already-approved containment (isolated route → ModelView
   abstraction later).

8. **Verdict: APPROVE WITH CONDITIONS** — conditions listed in §24 (anchor/pose
   vocabulary freeze before GLB authoring, rig experiment gate, AI→3D trial
   before scale-up, no cloth sim, no production touches until the integration
   phase).

## 2. Target State

A **DRESSED digital fashion doll**: a stylized, non-photorealistic mannequin
with elegant long limbs and a polished fashion silhouette, on which a user
eventually can (a) wear any garment with it *sticking to the body*, (b) change
pose freely (head, shoulders, arms, elbows, hands, torso, hips, knees, legs,

interaction — while the 2D production system remains intact until an explicit

## 3. Architecture Options (the critical question, §7 of the brief)

### 3.1 The options compared for DRESSED

| Option | Mechanism | Pros for DRESSED | Cons / failure modes | Verdict |
|---|---|---|---|---|
| **A. Rigid anchor-based clothing** | One static garment GLB parented to an anchor node (child of a bone) — exactly what the POC depth probe already proves | Trivially simple; zero skinning cost; perfectly deterministic; cache-friendly; matches how the 2D system thinks (one layer attached at an anchor) | **Cannot deform.** A sleeve stays straight when the elbow bends; a coat hem swings as one block when a leg lifts; garment penetrates the body at any joint angle ≠ bind angle. Gives "follows the bone" but not "sticks to the body" at joints | **Insufficient as the foundation** — but correct *permanent* home for accessories, and a legitimate Phase-4a stepping stone |
| **B. Bone-based skinned clothing** | Garment vertices carry `(bone indices, weights)` bound to the **same skeleton** as the body; a pose change deforms body and garment together | Industry standard; exactly satisfies "raise an arm → sleeve follows, shirt stays on torso"; deterministic; GPU-cheap (22 bones); pose-independent placement; supports body-type retargeting via shared bone names | Requires the skeleton first (the foundation decision); weights must be authored/computed; bad weights = shoulder tear; loose items (skirt hems) need hip-blend care | **Correct end state for all body-worn garments** |
| **C. Full cloth simulation** | Physics per frame (verlet/XPBD + body collision) | Perfect drape; "free-hanging" realism | Non-deterministic (breaks reproducible thumbnails — the "one mesh → all views" guarantee); CPU/mobile risk; instability and tuning burden; needs collision volumes; wrong genre — a wardrobe viewer needs *stable silhouettes*, and fashion dolls are famously **stiff** | **REJECTED** (aligns with freeform report §27 Extreme) |
| **D. Hybrid** | B for body-worn garments + rigid anchor attachment for accessories/props/short hair + (later, optional) a *tiny* secondary-motion layer (1–4 sway bones for skirt hem/long hair) | Per-asset-class rightness; staged delivery (rigid first, skinned next); no new engine features; every expensive path stays optional | Slightly more metadata (per-asset `skinning: rigid \| skinned`) | **RECOMMENDED** |
| **E. Surface-bound deformation without bones** (geodesic body→garment weights, no user-visible skeleton) and/or **parametric shells** (garment as a fitted surface generated from body measurements) | Attractive research paths; surface-binding is what auto-fitters use internally | But DRESSED *needs a visible skeleton anyway* for posing (brief §5) — a bones-less bind still ends up needing bone semantics; parametric shells are a *generation* technique, not an attachment architecture, and would replace the AI-garment pipeline wholesale | Rejected as the foundation; parametric generation may return later as *one* garment-creation method (decision then) |

### 3.2 Why not "A first, forever" (the tempting cheap path)

Rigid-first is fine as a **phase** (Phase 4 proves attachment with zero
skinning complexity), but choosing A as the *architecture* would make the
future posing requirement (brief §5 — bend elbows, raise arms, rotate torso)
impossible without a later rewrite: every garment would need rebinding from
scratch. The skeleton is cheap (~22 bones) and the pose future is explicitly
on the roadmap — so the foundation must be skeleton-compatible **from day
one**. D = skinned *by design*, shipped in stages.

### 3.3 The decisive product arguments

1. **"Clothing sticks to the body" = binding, not physics.** Skinning is the
   industry interpretation of exactly this requirement (character games,
   VTuber/fashion apps): deterministic, pose-independent, free per interaction.
2. **Determinism is a DRESSED invariant**: front/side/back consistency,
   thumbnails and reproducible renders assume one mesh → all views. Cloth sim
   breaks reproducibility; skinning preserves it.
3. **Cost invariant**: runtime deformation must never touch AI. A and B both
   satisfy it; C too, but fails on performance/determinism.
4. **The doll aesthetic helps**: fashion dolls have clean, semi-rigid
   silhouettes — skinned, semi-rigid fabric reads *correct* for the style, where
   a realistic game might demand more drape.

## 4. Recommended Architecture (one sentence + diagram)

**Option D — "skeleton-first hybrid": one shared humanoid skeleton is the
single source of motion; body-worn garments are skinned to it, accessories are
rigidly parented to bone-anchored nodes, hair is separate and head-weighted,
and no cloth simulation exists anywhere in the system.**

```text
                    DRESSED_MODEL (scene — unchanged contract)
                    ├── skeleton   root → pelvis → spine → chest → neck → head
                    │                            └→ clavicle_L/R → upperArm_L/R
                    │                               → lowerArm_L/R → hand_L/R
                    │                            └→ upperLeg_L/R → lowerLeg_L/R
                    │                               → foot_L/R
                    ├── body       (SkinnedMesh ← skeleton weights)
                    ├── anchors    head/torso/waist/shoulder_L/… = Object3D
                    │              children OF the relevant bones ← POC-compatible
                    ├── garment_*  (SkinnedMesh, SAME skeleton)  ← tops, pants, dresses…
                    ├── accessory_* (Object3D parented to anchor) ← shoes, bags, hats…
                    └── hair_*     (rigid→head, or skinned head/neck/chest)

POSE CHANGE   = FK joint rotations on the skeleton
              → body deforms + skinned garments deform + rigid children follow
              → zero AI · zero server calls · zero user re-placement

VIEW CHANGE   = yaw about +Y (contract unchanged) · camera never persisted
```

The contract's existing chain
`bone → anchor → (u,v,w) → rotation → scale → shell` was written for exactly
this future — the POC already implements the anchor/Object3D mechanics with a
reparented probe child; skinning *adds* deformation under the same bone roots.

**Frozen before any further GLB authoring (condition C1):** the full anchor
vocabulary (the 15 existing 2D names, sided where needed → §6/§8), the bone
name list (§6), the slot table (§9), and a contract version bump (`poc-v1` →
`v2`) when the skeleton lands. Anchors bound to bones replace today's
model-space rest positions in `asset-sources.ts` **per asset**, exactly as that
file already documents ("a different GLB legitimately ships a different anchor
map").

**Per-garment processing pipeline (deterministic except step 2):**

```text
1. ASSET EXISTS      GLB in bind pose + vertex/texture material   (author/AI, offline)
2. (optional) AI     classify slot/anchor, reconstruct mesh, complete hidden back
3. BIND              compute or read skin weights against the DRESSED skeleton
4. VALIDATE          bounds/intersection/weight-normalization/contract checks
5. STORE             one file per unique design (hash), CDN-cacheable
6. RUNTIME           load → parent to skeleton → pose changes deform it → render
                      (NO AI at any runtime step — steps 3–6 are pure math)
```

## 5. What "clothing sticks to the body" must mean technically (§9)

### 5.1 The four distinct layers (keep them separate — this is what prevents over-engineering)

| Layer | What it is | Where it lives | Mutability |
|---|---|---|---|
| **1. Asset geometry** | The physical garment: mesh, materials, textures, **bind pose** | GLB file | Immutable per version |
| **2. Attachment metadata** | *How* it attaches to a DRESSED body: skinning type, slot, default anchor(s), skeleton/contract version it was bound for, body-type compatibility, default depth `w`/offset, orientation rule | Small JSON/GLB `extras` row (future `garment_assets` / reuse `wardrobe_item_ai_assets`-style table) | Immutable per version |
| **3. User placement** | *Where the user wants it*: `placement3d = { anchor?, u, v, w, rx, ry, rz, s[, sx, sy] }` — sibling of 2D `placement`, lazy/NULL-default | `wardrobe_items.placement3d` (future column; **not created now**) | Per user, per item |
| **4. Deformation** | *How it reacts when the body moves*: skin weights (for skinned assets); nothing (for rigid — the parent bone does it) | Inside the GLB's skin (`inverseBindMatrices` + weights) | Immutable per version |

**Placement (3) never changes when the pose changes** — pose movement is
*layer 4's* job. Users re-place an item only to fix styling, never to repair it
after posing. That is the precise meaning of "sticking".

### 5.2 Metadata: what is actually necessary (minimum viable set)

**Include (v1):** `skinning: "rigid" | "skinned"` · `slot` (behavior unit) ·
`anchor` (default attach node) · `contractVersion`/bind-pose identifier ·
`baseTypes: ["woman","man", …]` compatibility · default `w` thickness offset
(skin clearance, ≈0.005–0.02 m) · orientation (front axis = asset-local +Z).

**Exclude now (YAGNI):** collision settings (no cloth sim exists) ·
deformation-rule DSLs · per-side behavior flags · fit-solver parameters ·
body-offset fields (that is placement, layer 3) · LOD rules (defer until
measured) · per-pose correction tables (blend shapes are a *later, evidence-
gated* add-on for shoulder correction, not metadata).

**Do not duplicate:** category/label/price already live in `wardrobe_items`;
the slot table maps category → slot once in `lib/shared` (navigation report §8:
13 slots + hair, exclusions like dress ⇄ top/bottom handled as slot rules, not
`if (category === …)` checks).

### 5.3 The three rule statements

1. **Attachment (layer 2+3) answers WHERE; deformation (layer 4) answers HOW IT
   BENDS.** They are configured independently — a jacket can be skinned (layer
   4) *and* have a user placement (layer 3).
2. **AI never writes layers 3 or 4 at runtime** (it may *propose* layer-2
   slot/anchor during offline asset creation — freeform report §9).
3. **One asset → deterministic fit** for every compatible body: same skeleton
   names ⇒ same deformation; differences in body shape are handled at bind/
   registration time, never per user at runtime.

## 6. Skeleton Recommendation (§10)

### 6.1 The proposed skeleton — ~20–22 bones, nothing more

```text
root                         # ground-stable whole-model node (feet origin)
└─ pelvis                    # hip center; base of pose motion
   ├─ spine                  # lower torso / waist bend
   │  └─ chest               # upper torso; shoulder anchor parent
   │     ├─ neck
   │     │  └─ head          # hat/glasses/hair/earrings/face anchors
   │     ├─ clavicle_L ─ upperArm_L ─ lowerArm_L ─ hand_L
   │     └─ clavicle_R ─ upperArm_R ─ lowerArm_R ─ hand_R
   ├─ upperLeg_L ─ lowerLeg_L ─ foot_L
   └─ upperLeg_R ─ lowerLeg_R ─ foot_R
```

Count: root, pelvis, spine, chest, neck, head (6) + 2×clavicle (2) +
2×(upperArm, lowerArm, hand) (6) + 2×(upperLeg, lowerLeg, foot) (6) =
**20 core bones** — no toes (foot pivots at ankle for every fashion pose).
**This is exactly the list proposed in the brief and it is sufficient**
(INFERRED from garment + pose requirements; matches readiness §6 "one
canonical skeleton per body family").

**Naming:** frozen in the contract together with the skeleton version —
lowercase snake with `_l/_r` suffixes (e.g. `upperarm_l`) is recommended; the
style matters less than **freezing it once** (renaming later invalidates every
GLB). Also freeze the anchor→bone binding table with it:

```text
head→head · face/ears→head · neck→neck · shoulders→clavicle_l/r
torso→chest · waist→spine · hips/dress→pelvis/chest · left-hand/right-hand→hand_l/r
knees→lowerleg_l/r · ankles→lowerleg_l/r · feet→foot_l/r · full-body→root
```

(Exact knee/ankle choices are part of the C1 freeze — they only need to be
*one* documented answer.)

### 6.2 Explicitly NOT in v1 — and the condition that brings each back

| Feature | v1? | When it becomes necessary |
|---|---|---|
| **Fingers** | **No** — doll mitt hands (the current body has mitten+thumb) are a legitimate style choice; hand-level pose covers fashion gestures | When product requires hand posing beyond 1–2 presets (e.g. holding a bag by fingers rather than a wrist anchor). `thumb/…` bones are *additive children* of `hand_l/r` later; existing weights unaffected |
| **Toes** | **No** | Never (a heels variant changes foot *shape*, not toe bones) |
| **Twist bones** (`upperarm_twist`, `thigh_twist`) | **No** | Only if pose QA shows "candy-wrapper" collapse of forearm/thigh when shoulder/hip rotates >~90°. Mitigation order: (1) 50/50 weight spread at bind, (2) corrective blend shape, (3) *then* twist bones. Near-cylindrical doll limbs tolerate rotation well — likely never needed (UNVERIFIED until pose tests run) |
| **Facial bones** | **No** — stylized static face; identity comes from master + personal identity layer, not expression | Only if animated expressions become a product feature (not in the current vision) |
| **IK** | **No as data** — IK is a *control/UX* technique over FK bones, not skeleton content | Phase 5 UX: if FK sliders feel clumsy, a two-bone arm/leg IK handle is a small client-side solver. Skeleton unchanged |
| **Helper / dynamics / cloth bones** | **No** | Optional Phase 7 "secondary motion" experiment (skirt-hem sway, hair sway) *only* if static skinned results feel too stiff — few-bone deterministic springs only, never full cloth sim |
| **Eye/jaw bones** | **No** | Never for the doll scope |

**Sizing across body types:** one skeleton *definition* (same names, same
hierarchy, same count) instantiated per body type with type-specific rest
lengths — see §14.

## 7. Clothing Recommendation (§8 — per garment type)

| Garment | Attachment | Deformation | Notes |
|---|---|---|---|
| T-shirts / tops / shirts / sweaters | **Skinned** (spine, chest, clavicle, upperArm ± lowerArm) | Skinned | Sleeves weight to the arm chain; body to the torso chain; blend across the shoulder |
| Jackets / coats | **Skinned** (same as top + `hand` for long sleeves) | Skinned | Open front: both panels weight to torso; hem blends to pelvis. Coat = jacket logic with a larger skin clearance `w` |
| Jeans / trousers / shorts | **Skinned** (pelvis, upperLeg, lowerLeg) | Skinned | Crotch vertices blend pelvis↔upperLeg to survive wide stances |
| **Skirts** | **Skinned with hip blend** (pelvis + both upperLeg, distance-weighted) | Skinned | Hardest case — §7.1 |
| **Dresses** | **Skinned** = union of top + skirt weighting | Skinned | Slot `one-piece` excludes top/bottom (slot table) |
| Jumpsuits | **Skinned** = union of top + trousers weighting | Skinned | One asset, slot `one-piece` |
| Socks | **Skinned** (lowerLeg/foot) | Skinned | Thin; behaves near-rigid either way |
| Shoes | **Rigid → `feet` anchor on `foot` bone** | Rigid | Only one joint (ankle); skinning buys nothing. Heels = foot-shape variants later |
| Sunglasses / glasses | **Rigid → `face` anchor on `head`** | Rigid | |
| Jewelry (earrings, necklaces, bracelets, watches) | **Rigid → head/neck/hand anchors** | Rigid | Bracelets/watches on `hand`; tiny meshes |
| Handbags | **Rigid → `right-hand`, or `shoulders`-side for shoulder bags** | Rigid | The known 2D shoulder-bag pain point becomes deterministic metadata (freeform §18) |
| Hats / hair-accessories | **Rigid → `head` anchor on `head`** | Rigid | |
| Scarves | **Skinned** (neck + chest blend); rigid → neck for short scarves | Skinned preferred | Long loose ends: v1 weights to neck/chest (stiff but stable); sway bones later if wanted |

### 7.1 The hard cases, honestly

- **Skirts/dresses (hem vs legs):** pure pelvis-weighting keeps the skirt
  rigid with the hips — correct standing (the default doll stance), wrong when
  legs split wide (hem doesn't part → leg pokes through). Blend weighting (hem
  vertices take partial `upperLeg` weights) lets the skirt *part* with the legs
  but creases at the hip. **v1 answer:** blend weighting + fashion pose presets
  that keep legs modest (doll convention); revisit a `skirt` helper bone only
  if real QA complains. No cloth sim.
- **Loose sleeves / flares:** weight to the arm chain; at large flares the
  fabric can intersect the hip when the arm is down — solve with skin clearance
  `w` + A-pose arm clearance (§11), not physics.
- **Coats:** jacket logic; open front panels hang from the torso. Sitting
  poses may intersect the thighs — acceptable for v1 (fashion viewer, not a
  simulator).
- **Long hair:** §12. **Bags in-hand:** rigid wrist anchor; a bag never
  deforms with fingers because we do not have fingers.

### 7.2 Why not cloth sim for "the difficult ones"

Every difficult case above degrades *gracefully* with skinning (occasional
intersection in extreme poses — a QA-polish problem: pose limits + weights),
while cloth sim degrades *catastrophically* (mobile perf, jitter,
non-deterministic thumbnails — an architecture problem). Choose the polish
problem.

## 8. Body Recommendation (§12) — retain, rig, gate; do not rebuild yet

### 8.1 The options for the body workflow

| Option | Assessment |
|---|---|
| **Keep procedural as-is** | The generator already produced a contract-valid, proportion-correct, visually credible doll (this was proven by the body experiment). **But** the mesh is a merge of *overlapping closed shells* (separate arm/leg/torso/head shells) with no UVs and no deformation-oriented edge loops. Rendering + anchors: fine. **Skinning: unproven — this is the gate** |
| **Regenerate procedurally with better topology** | Continuous-branching torso↔limb topology (true edge loops through shoulder/hip) is the *hard* problem of procedural humanoids; the current script's ring-tube approach cannot branch cleanly. Feasible only as a major rewrite — not recommended |
| **Sculpt/retopo in Blender (free, open source)** | Industry-standard path to rig-ready topology: sculpt → quad retopo with loops at shoulder/elbow/knee/hip/neck/wrist → bone-heat auto-skin → GLB. One-time manual cost. **No paid service.** Requires installing Blender (local tool; approval item) |
| **Paid remesh/AI topology services** | **Excluded** — paid, and unnecessary for one master asset |
| **Buy/open-source character meshes** | License verification burden + style mismatch + still needs adaptation; rejected previously — unchanged |

### 8.2 The recommendation: evidence-gated hybrid

1. **Retain `dressed-base.glb` as the starting point** — it is the
   proportions master, the anchor-map reference, and the Phase-2 rig test
   subject. It is NOT deleted or "replaced by a paid model".
2. **Phase 2 = rig THIS mesh** with *computed* weights (nearest-bone-segment
   falloff computed offline in Node — no DCC needed for a first pass — or
   Blender bone-heat if installed) and **pose-test it** through the fashion
   pose envelope: ±75° shoulder raise, 90° elbow, hip flexion, head turn,
   torso twist. Key observation: **weights are assigned per vertex in world
   space, not per shell** — vertices of two overlapping shells near the shoulder
   receive similar blended weights, so interpenetration seams may well move
   *together*. This must be *measured*, not assumed either way.
3. **Gate decision after the pose test:**
   - **Seams hold** (no visible tearing/holes in the envelope) → keep the
     procedural body; invest remaining effort in doll *styling* (§13) only.
   - **Seams tear** at shoulder/hip → Blender retopology of the *same
     proportions* (the generator's parameters remain the design reference),
     auto-skin, export as `dressed-base-v2.glb`, re-validate anchors. This is
     also the moment to add UVs if textures are wanted.
4. **Topology requirements for any v2 body (for the Blender pass):** edge loops
   around shoulder socket, elbow, knee, hip crease, neck, wrist; clean
   quad-dominant limbs; single continuous surface (manifold) so weights can't
   split across an interpenetration seam; keep total tris ≤ ~40–50k (current
   49,960 is already at the top of the band — see §16); keep vertex colors or
   move to a small texture atlas.
5. **Do NOT** start a Blender sculpt before the Phase-2 evidence, and do NOT
   introduce any paid tool (condition C6).

**Why this ordering matters:** rebuilding the body first would spend the most
expensive effort (sculpt/retopo) *before* knowing whether it is needed, and
would freeze proportions before the doll-style parameter targets (§13) are
reviewed. Decisions are cheap; geometry is expensive (freeform §31 ordering
principle) — keep it.

## 9. A/T Pose Recommendation (§11)

| Pose | Verdict for DRESSED |
|---|---|
| **T-pose** | **Not the master.** Pros: textbook shoulder weights, sleeves isolated from the torso. Cons: wrong silhouette for a fashion doll and for QA ("does this top look right?"); fights the arms-down 2D heritage (the 2D prompt explicitly draws sleeves down); costs the same weight effort in reverse when lowering arms; AI-reconstructed garment meshes are pose-agnostic anyway (fitting is registration, not pose matching) |
| **A-pose (tight, arms ~10–20° — today's)** | Close, but arms risk touching the hip → weight bleeding arm↔hip and sleeve/torso intersection at rest |
| **Relaxed A-pose, arms ≈30° clear, symmetric, feet slightly apart, palms in, neutral spine** | **RECOMMENDED as the master bind pose.** Longest clearance from every failure mode: clean armpit for weights, garments fitted without arm-torso intersection, doll-appropriate silhouette, minimal distance to *any* display pose (weight range is smaller than from T) |
| **Fashion-model stance (contrapposto, bent knee, cocked hip)** | **Never as bind pose.** As a *runtime pose preset* — yes: display poses are data (joint rotations), authored on top of the neutral rig |

**Rules:**
1. **Bind pose ≠ display pose.** The body binds neutral; every fashion stance
   is a pose preset (FK rotation set) applied at runtime — deterministic, zero
   AI, and reusable across body types with the same skeleton.
2. **Garments are authored/fitted in the bind pose** (all of them, always) —
   this is what makes one garment asset reusable.
3. **Widen slightly vs today** during the next body iteration (Phase 3): target
   arms ~30° from vertical with hands visibly clear of the hips. (INFERRED
   need; exact current angle unmeasured — UNVERIFIED.)
4. Keep T-pose export as an *optional debugging* variant of the rig if the
   Blender path is taken — cheap to produce, never the shipping master.

## 12. Adult / Teen / Child (+ the existing woman/man) (§14)

**Code reality first:** today's vocabulary is `woman | man`
(`CLOTHING_BASE_TYPES`) with per-type anchor-Y overrides (`MAN_ANCHOR_Y`) —
adult/teen/child is a *future* concept discussed in reports, not schema
(CONFIRMED). The question generalizes to: many body types, one garment.

| Option | Verdict |
|---|---|
| **One literal skeleton object shared by all types** (same rest lengths) | Impossible in practice — a child's arm is not an adult's arm scaled; rest lengths must differ |
| **Separate skeletons per type (independent hierarchies)** | Rejected — pose retargeting and garment weights become per-type translation tables; guarantees divergence |
| **Shared skeleton *vocabulary* with body-specific geometry + rest lengths** | **RECOMMENDED.** Same bone names/hierarchy/count everywhere; each body type = (geometry GLB, rest-pose parameters, anchor map). A pose = joint-angle set that applies to *any* type; a skinned garment's weights reference bone *names*, so the same GLB loads on any type whose skeleton has those names |

### The fitting honesty (what "one garment → all types" can and cannot mean)

- **Same-skeleton types with similar proportions (woman ↔ man, adult ↔ teen):**
  one garment asset fits deterministically; small shape differences are absorbed
  by (a) the garment's bind clearance and (b) an optional per-type regional
  scale applied at load (data, not a new asset). Tolerance target: reuse when
  shape delta ≲ ±15 % (freeform §15.3 placeholder — UNVERIFIED, validate in
  Phase 6).
- **Child (distinct chibi proportions):** the same mesh scaled will *look*
  wrong (length ratios differ). Honest answer: same skeleton vocabulary =
  technically loadable, visually gated; if QA fails, children get **variant
  assets sharing the same design hash** (regenerate/refit once per body type,
  reuse across users) — still one *design*, N *fits*.
- **Precedent already in 2D:** `dressedAnchor(anchor, baseType)` shows DRESSED
  treats anchor maps as per-type data (CONFIRMED). 3D extends the pattern:
  anchor map + rest lengths + geometry per type, skeleton *names* shared.
- **Recommendation:** build woman (adult) first through Phases 2–7; add **man
  as the second type at Phase 9** to prove cross-type pose + garment reuse
  *before* teen/child exist; teen/child only after fit-tolerance evidence.

  with thumb, arched simplified feet. Explicitly *on-brand* for a fashion doll,
  which removes pressure to sculpt realistic anatomy.

## 14. AI Boundary (§17) — confirmed sound

The proposed separation is technically sound and matches the shape of the 2D
system (background jobs + caches). Restated as a hard contract for 3D:

### AI **may** (offline, once per asset, quota/cost-tracked)

1. Identify/classify an uploaded garment (slot, anchor, side) — a *proposal*,
   accepted deterministically.
2. Reconstruct/complete the 3D garment mesh from image(s) (photo → GLB),
   including inferring hidden back geometry when flagged (freeform §11 levels).
3. Assist validation (reject/flag bad reconstructions — human loop).
4. (Existing, unchanged) identity/character images and the 2D final-look
   image — already cached (`outfit_key`, per-item asset cache).

### AI **never** (runtime, in any circumstance)

1. Posing, IK, deformation, skinning, attachment resolution.
2. Rotation, camera, front/side/back derivation, thumbnails, LOD — all are
   deterministic renders of one mesh ("one mesh → all views").
3. Placement math (`placement3d` resolution), slot navigation, gestures.
4. Regenerating anything identical (hash-gate) or per-user copies of shared
   geometry.
5. **Any call at all while the user merely moves/rotates/poses the model or
   swaps an already-created garment.**

### Why the boundary is safe to keep

- Runtime only *consumes* GLBs + math (verified: the current 3D stack imports
  no AI/Supabase module — CONFIRMED).
- All AI entry points are already background-job patterns with reservation
  accounting (existing 2D flow), so 3D reconstruction slots into the same
  queue/cost machinery — subject to the cost-protection architecture being
  implemented before scale (§Cost).

## 15. Performance (§19) — budgets and what to avoid

### 15.1 Budgets (target: mid-range Android + iPhone Safari, WebGL)

| Item | Budget / status |
|---|---|
| Draw calls | ≤ ~15 total (1 body + ≤5 garment slots × ~1–2 meshes + hair + debug) — trivial; the 2D system's 5-item cap should carry into 3D |
| Bones | ~20–22 — GPU skinning cost negligible (three.js uses bone textures) |
| Triangles | Body 49,960 today (**top of the band**); whole scene target ≤ ~120k tris; garments ≤ ~10–15k each. Decimate/Draco only after measurement |
| Textures | Body: none (vertex colors — big win). Garments: ≤ 1024² (2048² max); KTX2 later if texture count grows (readiness §15) — UNVERIFIED need |
| GLB size | Body 1.2 MB uncompressed, loaded on demand. Monitor total per-outfit payload (5 garments + hair + body); Draco/meshopt is the lever *after* measurement |
| Memory / contexts | Already handled: one WebGL context, idempotent dispose, visibility pause (CONFIRMED in `viewer.ts`) |
| Shadows / post | **None in v1** (no shadow maps, no bloom/DOF). Optional cheap blob shadow under feet later |
| Animation | Poses are static FK transforms — update skeleton, render. No physics, no animation graph |
| Render loop | Keep on-demand rendering (render on interaction, not continuous idle 60 fps) — already the POC design |

### 15.2 Things to avoid (the explicit do-not list)

1. **Cloth simulation** anywhere on the client (CPU + instability).
2. **Continuous idle rendering**; never a second WebGL context.
3. **Per-garment unique materials/shader graphs** — share materials; vertex
   colors where possible.
4. **Loading all outfits/garments up front** — swap-on-demand + cache (slot
   navigation §11: max 1 in-flight load per slot, fail-closed).
5. **Post-processing chains and real-time shadows** before a measured need.
6. **Runtime weight computation** at pose time — weights are baked when the
   asset is created.
7. **Draco/KTX2/transcoder machinery before the payload actually hurts** —
   readiness §15 stays the *when-measured* plan.
8. **Many simultaneous animated characters** — the product shows one model.

## 16. Cost (§18) — the architecture IS the cost control

### 16.1 The economic shape

```text
PAY:  once per UNIQUE garment design  [AI: classify + reconstruct + (opt.) back-fill]
      ≈ 1–3 AI calls ≈ $0.064/call (telemetry) + reconstruction $0.20–0.50
      (UNVERIFIED, freeform §21 estimate) → hash-gated, background job, quota-tracked

FREE: every pose change · every rotation · every view snap · every slot swap of an
      existing garment · every thumbnail/render · every body-type load of a fitted
      asset · every user after the first
```

### 16.2 Why zero-AI interactions hold *by construction*

1. **Runtime has no AI code path** (§14) — it reads GLBs and computes matrices.
2. **One asset serves all users** of a compatible design *in principle*; within
   one user it is guaranteed by the existing per-item cache pattern.
   Cross-user reuse is a legal/storage decision (freeform §30) — engineering
   ready, decision pending.
3. **All views are renders of one mesh** — front/side/back/thumbnails never
   become "3 more generations" (z-axis rule preserved).
4. **Pose ≠ asset** — a pose preset is a few floats; a garment must not
   regenerate to follow a pose *because it is skinned* — the entire point of
   Option D over "AI re-places the garment per pose".
5. **Caching layers:** CDN/HTTP cache for static GLBs (CONFIRMED: the served
   GLB is byte-identical to disk) + in-memory geometry cache per session.

### 16.3 The economic risks (honesty — inherited, not new)

- **The audit gates Phase 8:** unlimited clean-preview calls, refund-on-failure
  retries, reservation-token leak, moderation-before-quota (audit A4–A7). 3D
  adds a new generation type with a **higher unit cost** (3–8× an image call) —
  the cost-protection architecture (global circuit breaker, budget ledger,
  attempt caps) must land **before** reconstruction scale-up, not after.
- **Reconstruction retries multiply cost** — validation gates + acceptance
  loop (freeform §25) are a *cost* feature, not only a quality feature.
- **Never charge per user for shared geometry** — bodies are procedural/
  parametric (free); per-user identity (head/face) remains the existing 2D
  per-user AI cost.
- **Verdict:** DRESSED stays affordable *iff* the once-per-asset rule is
  enforced technically (hash-gate + no per-view generation + no per-pose
  regeneration). This recommendation guarantees all three.

4. **Should clothing be skinned?**
   **YES, as the end state for all body-worn garments**; rigid anchor
   attachment for accessories/shoes/hats/bags. Rigid may ship first (Phase 4a)
   as a staged milestone, but the foundation is skeleton-compatible from day one.

5. **Do we need cloth simulation?**
   **NO.** Not v1, not foreseeably. Rejected for determinism, mobile cost,
   instability, and product fit (fashion dolls are stiff). Revisit only with a
   concrete product need — never by default.

6. **Should clothing follow bones rather than AI?**
   **YES — exclusively.** Runtime deformation/attachment is pure math on bones;
   AI appears only offline, once per unique asset. This is the cost model *and*
   the correctness model.

7. **What is the minimum skeleton?**
   `root, pelvis, spine, chest, neck, head, clavicle_l/r, upperarm_l/r,
   lowerarm_l/r, hand_l/r, upperleg_l/r, lowerleg_l/r, foot_l/r` ≈ **20 bones**.
   No fingers/toes/twist/face/IK/helper bones in v1 — each has an explicit
   re-entry trigger (§6.2).

8. **What base pose?**
   **Relaxed A-pose, arms ≈30° clear of the torso, symmetric, feet slightly
   apart** (bind pose). Display/fashion poses are runtime presets; garments are
   always fitted in bind pose. T-pose only as an optional debug export.

9. **Should hair be separate from the body?**
   **YES** — bald master (already encoded in the GLB `extras.role`); hair = own
   asset, rigid→head (short) or skinned head/neck/chest (long).

10. **Should accessories be separate assets?**
    **YES** — rigid GLBs parented to bone-bound anchors; no dedicated accessory
    bones, no skinning, no physics.

11. **Can one garment asset support multiple DRESSED body types?**
    **YES where proportions are similar** (woman↔man, adult↔teen) via shared
    skeleton *names* + bind clearance/optional per-type load-time scale;
    **conditionally for child** proportions (expect variant assets sharing one
    design hash). Prove with `man` in Phase 9 before promising teen/child.

12. **Can this architecture support future full posing?**
    **YES** — FK joint rotation on the shared skeleton already covers head,
    shoulders, arms, elbows, hands, torso, hips, knees, legs, feet; skinned
    garments and rigid children follow by construction; IK/limits/pose
    libraries are additive UX layers, not architecture changes.

13. **Can it support future clothing deformation?**
    **YES** — that is exactly what skinning *is* (weights in the GLB);
    pose-corrective blend shapes and few-bone sway are optional later upgrades.

14. **Can it support AI → 3D garments?**
    **YES, with conditions** (freeform §32 echoed): hash-gated once-per-asset
    generation, validation gates, ~10-garment trial (Gate C) before scale-up,
    back-side inference limits understood, no per-view/per-pose generation.

15. **Can it remain affordable?**
    **YES iff** the once-per-asset rule is enforced (this architecture
    guarantees no AI per pose/rotation/swap) **and** the audit's cost-protection
    gaps (A4–A7) are fixed before reconstruction scale-up.

16. **Can it remain performant in a browser?**
    **YES** — ~20 bones, ≤5 garments, ≤~15 draw calls, no cloth sim, no
    shadows/post in v1, on-demand rendering, body at 49,960 tris (watch item —
    decimate/Draco only if measured). Budgets in §15.

17. **Can it coexist safely with the 2D system?**
    **YES** — additive by construction: `placement3d` sibling (lazy, NULL),
    renderer-agnostic outfits/selection, isolated route until Phase 10,
    `ModelView` wrapper (not a rewrite), 2D untouched and permanent fallback.

18. **What is the biggest technical risk?**
    **Skin deformation quality at the shoulder/hip on the overlapping-shell
    procedural body** — it gates the body, the garments and the posing UX, and
    everything downstream assumes it works. Runner-up: AI→3D garment quality
    (external, gated by Gate C). Third: premature vocabulary drift (mitigated
    by C1 freeze).

19. **What should we test FIRST?**
    **Phase 2: rig the current GLB with computed weights and pose-test it**
    (Gate A) — cheapest decisive experiment; answers keep-vs-retopo and
    de-risks everything. Immediately followed by Phase 4's one-garment attach
    test (Gate B) and, once fitting exists, the 10-garment AI trial (Gate C).

20. **What should we absolutely NOT build yet?**
    Cloth simulation · `placement3d` migration / any DB schema · wardrobe or 2D
    integration · AI garment generation at scale (or before cost protection) ·
    finger/twist/face/IK bones · per-view image generation · strand hair ·
    toon-outline overhaul · teen/child variants · cross-user asset sharing ·
    any paid service. (All deferred by explicit condition or gate above.)

## 21. Final Recommendation (§24)

### APPROVE WITH CONDITIONS

The proposed direction — a stylized, poseable **DRESSED fashion doll** with
**skeleton-based clothing that follows the body** — is **technically sound**:
it fits the existing contract, the asset architecture, the AI/cost model, the
performance envelope of a browser Astro app, and the 2D-safety requirement.
No architectural problem was found that warrants rejection. The conditions
exist because three unknowns are *genuinely* unproven and cheap to test early.

### Conditions (all must hold; violation → re-evaluate)

- **C1 — Freeze the vocabulary first.** Full sided anchor set (15 names),
  bone names, anchor→bone table, slot table, bind pose, and contract `v2`
  are documented **before** any skeleton-carrying GLB or garment asset is
  authored. (Assets bake these in; renames invalidate them.)
- **C2 — The rig experiment gates the body.** Rig the *current* `dressed-base.glb`
  with computed weights and pose-test it (Gate A) **before** any Blender/
  rebuild work. Keep-vs-retopo is an evidence decision, not a taste decision.
- **C3 — Bind pose locked before garments.** Relaxed A-pose ≈30° arm clearance
  becomes the contract pose; every garment is fitted in it; fashion stances are
  presets only.
- **C4 — AI→3D stays gated.** The ~10-garment trial (Gate C) must be human-
  rated before any pipeline scale-up, and the audit's cost-protection fixes
  (A4–A7) must be live before any quota-exposed reconstruction runs. Zero AI
  in the runtime remains absolute.
- **C5 — No cloth simulation; no production touches.** No wardrobe/Supabase/2D/
  prompt changes; no `placement3d` migration; no merge/push/PR — all deferred
  to Phase 10 or explicit approval. 2D stays the default and the fallback.
- **C6 — No paid services.** Blender (if used) is a local free/open-source
  tool whose installation requires explicit approval; anything paid requires
  explicit approval, marked as such.
- **C7 — Performance budgets are enforced at review time** (§15): ≤5 garments,
  ≤~120k tris scene, no shadows/post/cloth in v1, on-demand rendering.

### What would flip this to REJECT

Gate A fails *and* the only available fix requires paid tooling or a licensed
character asset; **or** Gate C shows reconstruction quality unusable on
DRESSED's garment mix without a per-view/per-pose generation fallback (which
would break both cost and consistency invariants); **or** an unforeseen need
for true cloth drape proves central to the product (it is not, today).
